# KAN-186: Yield operation state and idempotency controls

KAN-186 implements the local P6-E21-TSK01 command boundary for `ALLOCATE`,
`WITHDRAW`, and `REBALANCE`. It does not contact a yield provider, submit an
on-chain transaction, deploy infrastructure, or incur a provider charge.

## State model

Yield operations reuse the canonical ledger transaction lifecycle from KAN-42:

`CREATED -> QUOTED -> USER_APPROVED -> SUBMITTED -> PENDING -> SETTLED`

The existing canonical failure and full-reversal edges also apply. The shared
ledger transition normalizer validates commands in the application, and the
`transition_ledger_transaction_state` database function validates them again
while holding the transaction state lock. Stale expected states, unsupported
edges, and mismatched reasons fail without appending an event.

Each operation is permanently bound to one actor account, operation type,
ledger transaction, plan reference, and quote reference. Plan and quote
references are opaque UUIDv4 identifiers; this slice does not define or copy a
yield-discovery payload.

## Idempotency and submission

The application accepts a bounded printable idempotency key, hashes it with a
domain-separated SHA-256 contract, and never sends or stores the raw key. A
command claim is scoped by actor, command kind, contract version, and key
digest. Its request fingerprint includes every command field that changes the
operation.

- An exact retry returns the original immutable command result.
- Reusing a key for a different fingerprint fails with `Y8601`, exposed as the
  fixed `YIELD_IDEMPOTENCY_CONFLICT` application error.
- Moving to `SUBMITTED` allocates exactly one submission/outbox identifier.
- Deferred command-completion and outbox foreign keys require the transition,
  submission record, and `yield.operation.submit` job to commit together.
- A replay does not enqueue another provider/on-chain adapter job.

No provider or chain adapter is implemented by this ticket. The outbox job is
the durable handoff boundary for a later worker.

## Immutable evidence

Migration `0012` adds the operation projection plus append-only transition,
command, command-result, and submission records. Every transition records:

- verified actor account and correlation identifier;
- source effective time and database-controlled recorded time;
- previous state, next state, and canonical reason;
- ledger transaction and book references; and
- a journal reference for `SETTLED` and `REVERSED` transitions.

The transition identifier is also the canonical ledger lifecycle event
identifier. Audit rows cannot be updated, deleted, or truncated, and rollback
is refused once retained yield-operation evidence exists. Runtime principals
receive no direct table DML; the API role receives only the two fixed
security-definer command functions.

## Implementation boundary

- `apps/api/src/yield-operations/domain` owns command validation and hashing.
- `apps/api/src/yield-operations/application` resolves the trusted actor and
  correlation context.
- `apps/api/src/yield-operations/infrastructure` composes PostgreSQL and the
  transactional outbox.
- Migration `0012` owns durable concurrency, replay, audit, and ACL controls.

An HTTP controller/module, quote or plan storage, provider adapter, and outbox
consumer are intentionally outside KAN-186. Those surfaces should call this
service/repository boundary rather than duplicate its state or idempotency
rules.

## Local verification

The unit suites cover all three operation types, canonical/invalid edges,
trusted context, fingerprint conflicts, fixed persistence errors, and exact
retry behavior. The guarded infrastructure spec
`yield-operation-controls.integration-spec.ts` exercises the real PostgreSQL
functions, deferred outbox link, single-submission invariant, immutable audit,
and cumulative verifier when the marked loopback fixture is enabled with
`TEST_DATABASE_URL` and `RUN_INFRASTRUCTURE_INTEGRATION=1`.
