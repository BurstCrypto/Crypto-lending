# KAN-229: AWS billing guardrail control record

KAN-229 defines the account, cost, authority, and evidence gates that must be
satisfied before KAN-34 may create or execute a change set. Repository work for
this ticket is strictly **zero-deploy**: this work has not contacted an AWS
account, enabled a cost-management feature, or activated a resource,
subscription, trial, or paid service.

The committed [example control record](../infra/aws/billing-control-record.example.json)
is deliberately unusable for a cloud action. Every operational value remains
`NOT_APPROVED` or `NOT_RUN`. Its
[JSON Schema](../infra/aws/billing-control-record.schema.json) checks the exact
record shape; the
[semantic validator](../infra/aws/validate-billing-control-record.mjs) also
checks approval state, dates, thresholds, authority, independent verification,
and live-evidence status. A valid file documents authorization; it does not
grant IAM permission and is never itself permission to deploy.

The validator emits two distinct digests. The canonical record SHA-256 covers
the complete record, including live evidence, and is bound to any later KAN-34
change set. The control-configuration SHA-256 covers the stable account,
environment, ownership, budget, recipient-alias, anomaly mode/threshold/source,
mechanism, and fee fields that drive the deployed controls. Evidence can mature from `NOT_RUN` to `PASS`
without changing that configuration digest or forcing a notification-control
replacement.

The current KAN-34 template's default application counts are zero, but its

The proposed account template configures an account-wide, unblended AWS Budget

not an approved exclusion decision. The control record must explicitly review
credits, refunds, taxes, support, Marketplace purchases, shared-account spend,
data transfer, ECR, DNS/domain charges, and retained snapshots, keys, secrets,
and logs. It must never silently omit a cost category.

## Advisory control, not a spending cap

AWS Budgets and Cost Anomaly Detection are notification controls. They do not
make AWS free, reserve funds, block resource creation, stop tasks, or guarantee
that spend cannot pass a threshold. AWS says budget data is updated periodically
and notification delivery can lag; a threshold can therefore be exceeded before
an alert arrives. Forecast alerts also depend on sufficient history. See
[Managing your costs with AWS Budgets](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html)
and [AWS Budgets best practices](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-best-practices.html).

Cost Anomaly Detection also has learning and reporting delays, and a newly seen
service may need historical data before anomalies are useful. See
[Managing Cost Anomaly Detection](https://docs.aws.amazon.com/cost-management/latest/userguide/manage-ad.html).
KAN-229 configures notifications only: no automatic budget action, IAM action,
resource shutdown, or report subscription is authorized.

The no-paid-services requirement is fail-closed. Before activation, the finance
owner must recheck the current [AWS Budgets pricing](https://aws.amazon.com/aws-cost-management/aws-budgets/pricing/),
Cost Anomaly Detection terms, notification delivery path, and any Cost Explorer
API charges. The record schema defines these mechanism enum values:

- `AWS_BUDGETS`;
- `AWS_BUDGETS_AND_COST_ANOMALY_DETECTION`; or
- `EXTERNAL_CONTROL_WITH_REFERENCE`.

The current executable guard accepts only `AWS_BUDGETS` or
`AWS_BUDGETS_AND_COST_ANOMALY_DETECTION`. An
`EXTERNAL_CONTROL_WITH_REFERENCE` record requires a later reviewed
implementation and cannot authorize the current template. The fee decision must be one of
`NO_ADDITIONAL_CHARGE_CONFIRMED`, `FEE_APPROVED`, or
`REJECTED_DUE_TO_FEE`. Under the project's current no-paid-services constraint,
only `NO_ADDITIONAL_CHARGE_CONFIRMED` permits continuation.
`FEE_APPROVED` is part of the record vocabulary but requires a later, explicit
policy change; `REJECTED_DUE_TO_FEE` blocks Plan and Deploy. Merely opening or
enabling Cost Explorer is an account mutation and may configure an anomaly
monitor and subscription, so it is prohibited during local work. See
[Enabling Cost Explorer](https://docs.aws.amazon.com/cost-management/latest/userguide/ce-enable.html)
and [Cost Explorer pricing](https://aws.amazon.com/aws-cost-management/aws-cost-explorer/pricing/).

## Record and data-handling contract

The approved record contains the exact account ID and alias, approved role ARN,
application and control Regions, environment, application owner, finance owner,
cost center, escalation route, thresholds, non-personal recipient references,
expiry, mechanism, anomaly mode and thresholds, any approved existing-monitor
ARN, fee decision, authority lists, independent verification, and evidence
status. Decimal currency and percentage values are strings to preserve their
exact representation.

Do not put credentials, access keys, session tokens, secret values, personal
email addresses, personal names, or other PII in the record, Git, Jira, stack
parameters, or evidence. `warningRecipient` and `criticalRecipient` identify
approved distribution-role aliases only. The actual delivery address belongs in
the separately protected operator input used for an authorized deployment.
Use a non-default named AWS profile at execution time, but never record its
credentials. Keep the completed operational record and parameter material in an
access-controlled path outside the repository; do not overwrite and commit the
example.

The schema proves only syntax. The semantic guard must additionally require:

- `status: APPROVED`, a current approval window, and a current pricing window;
- a positive baseline and limit, with the limit not below the baseline;
- warning at 50, 60, or 70 percent and critical at 80 or 90 percent, with the
  warning below the critical threshold;
- non-production environment and exact account, role, Region, and application
  matches;
- approved non-personal owners, recipients, escalation route, and authority;
- an approved independent verification decision; and
- `PASS` for account/Region/role, warning delivery, critical delivery, and the
  retained-resource review. Anomaly delivery must be `PASS` when enabled and may
  be `NOT_APPLICABLE` only when anomaly detection is deliberately disabled.

The canonical record SHA-256 is evidence binding, not a secret. Any change to
the record invalidates the prior digest and requires review again.

## Authority matrix

All identities below are logical role references. Assignments are currently
`NOT_APPROVED`, and all live evidence is `NOT_RUN`.

| Decision or action                                                 | Required authority                   | Separation requirement                                                      |
| ------------------------------------------------------------------ | ------------------------------------ | --------------------------------------------------------------------------- |
| Estimate, exclusions, thresholds, pricing expiry, and fee decision | Finance owner plus environment owner | Implementer cannot self-approve                                             |
| Account ID, alias, role, and Region verification                   | Independent third-party verifier     | Must be neither founder/implementer and must not approve their own evidence |
| Billing-control Plan                                               | `authority.planApprovers`            | Written approval for the exact record and template digests                  |
| Billing-control Deploy                                             | `authority.deployApprovers`          | Separate approval after change-set review                                   |
| KAN-34 application Plan                                            | `authority.planApprovers`            | Requires live KAN-229 evidence first                                        |
| KAN-34 application Deploy                                          | `authority.deployApprovers`          | Separate approval after the application change set is reviewed              |
| Retain a resource or snapshot                                      | `authority.retentionApprovers`       | Owner, reason, expiry, and estimated ongoing cost required                  |
| Delete a resource or retained artifact                             | `authority.deletionApprovers`        | Exact identifiers and dependency impact required                            |
| Alert routing and escalation                                       | Finance owner plus environment owner | Both routes must be independently delivery-tested                           |

Because both founders are implementing the controls, the account verifier must
be an independent third party. The record stores only that verifier's approved
role alias; the protected evidence system stores any identity details.

## Exact workflow order

The ordering is mandatory. A failure or stale approval stops the workflow.

### Local phase: zero AWS calls

1. Leave the committed example at `NOT_APPROVED` / `NOT_RUN` and keep KAN-34
   cloud actions blocked.
2. Obtain the proposed account, role, Regions, owners, cost center, escalation
   route, and distribution-role aliases through the approved governance channel;
   do not query AWS yet.
3. Produce a current Region-specific estimate covering every resource and
   retained artifact above. Review the proposed credits/refunds treatment and
   every other inclusion or exclusion.
4. Select one mechanism enum, recheck current fees and feature side effects,
   and record the applicable fee-decision enum. Any additional charge blocks the
   current no-paid-services workflow.
5. Create the completed control record outside the repository, collect the
   environment-owner, finance-owner, Plan, Deploy, retention, and deletion
   authorities, and set a short approval and pricing expiry.
6. Run only the local schema, template, and formatting checks. The
   evidence-complete `approved` semantic mode must still reject the record while
   its live evidence is `NOT_RUN`; do not bypass or relabel that failure. Record
   the draft record and template SHA-256 values. No local check may be described
   as live AWS acceptance.
7. Obtain separate written authorization for the minimal identity-only AWS
   preflight. That authorization is not permission to create a change set.

### Authorized account phase

8. The independent third party uses the approved non-default profile and calls
   STS `GetCallerIdentity`, then verifies the account alias, approved role,
   application Region, and control Region before any change set. Record the
   result as `accountRegionRole: PASS`; a mismatch stops immediately. See
   [STS GetCallerIdentity](https://docs.aws.amazon.com/STS/latest/APIReference/API_GetCallerIdentity.html).
9. With separate read authorization, inventory existing budgets, anomaly
   monitors/subscriptions, Cost Explorer state, notification routes, and tags to
   prevent duplicate or conflicting account controls. Reconfirm API fees before
   making those reads.
10. Add the identity evidence, run the semantic validator in `bootstrap` mode,
    and obtain explicit approval to create one named billing-control change set.
    Bootstrap still requires approved, current cost, fee, authority, and
    independent-verification fields. Warning, critical, and retained-resource
    evidence may remain `NOT_RUN`; anomaly evidence must be `NOT_APPLICABLE` for
    `AWS_BUDGETS` or may remain `NOT_RUN` while an approved anomaly control is
    being created. Plan must bind the approved account, Regions, record ID,
    complete bootstrap-record digest, stable control-configuration digest,
    template digest, parameter digest, and stack tags. It must not execute the
    change set.
11. Review every create, update, delete, replacement, retention, recipient,
    Region, and cost effect. Resolve the replacement-gap procedure below before
    approving a replacement.
12. Obtain a distinct Deploy approval for that exact, unchanged change set, then
    execute only the reviewed change set.
13. Verify the live budget, optional anomaly resources, scope, tags, thresholds,
    recipient subscriptions, and retained-resource behavior. Delivery
    configuration alone is not evidence of receipt.
14. Perform authorized warning, critical, and, when enabled, anomaly delivery
    tests without deliberately creating billable application resources. Record
    UTC send/receive evidence and the recipient route. Failed or absent evidence
    remains `FAIL` or `NOT_RUN`, never `PASS`.
15. Complete the first retained-resource inventory, assign every item an owner
    and disposition, start the daily UTC review, update only the evidence fields,
    and run the evidence-complete `approved` semantic validation. Confirm that
    the control-configuration digest still equals the deployed stack tag. If it
    changed, stop: the operational configuration changed and requires a new
    reviewed KAN-229 change set plus any affected delivery tests.
16. Only after all required evidence is `PASS` and the final record digest is
    approved may a KAN-34 `Plan` be considered. Plan is an AWS operation and
    still requires its own authorization; KAN-34 Deploy requires another exact
    change-set approval. KAN-34 `CloudValidate` is a separate syntax-only AWS
    call that creates no stack or resource. It does not require live KAN-229
    evidence, but it remains blocked without explicit opt-in and the approved
    KAN-34 account, non-default profile, and Region.

## Replacement and notification-gap control

CloudFormation marks an AWS Budget's `NotificationsWithSubscribers` changes as
replacement. Other budget, anomaly-monitor, anomaly-subscription, name, tag, or
monitor-source changes can also replace a resource. A fixed physical name may
make create-before-delete fail, while delete-before-create can leave an alerting
gap. `DeletionPolicy: Retain` can also leave an account-level control behind
after a stack is removed. See the CloudFormation references for
[AWS::Budgets::Budget](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-budgets-budget.html),
[budget notifications](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-properties-budgets-budget-notificationwithsubscribers.html),
[AWS::CE::AnomalyMonitor](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-ce-anomalymonitor.html),
and [AWS::CE::AnomalySubscription](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-ce-anomalysubscription.html).

A Plan containing a delete, replacement, or retention change must fail closed
until a distinct retention/deletion approval names every physical resource. The
approved transition must freeze application plans, inventory the old control,
create or identify the replacement without a naming collision, prove new
delivery, retain the old route until the new route passes, separately authorize
old-resource deletion, and then update the control record and digests. If dual
operation is impossible, document and approve the exact expected gap and a
manual escalation route before proceeding. Static CloudFormation status cannot
prove recipient confirmation or notification delivery.

## Daily retained-resource inventory

After the first authorized account action, a retained-resource review is due
once per UTC day, including days when an application stack is absent. It must
use service-native inventory or another approved complete source and cover:

- CloudFormation stacks and `REVIEW_IN_PROGRESS` placeholders;
- Budgets, anomaly monitors, anomaly subscriptions, and notification routes;
- KMS keys and aliases, Secrets Manager secrets, RDS instances and snapshots,
  ElastiCache replication groups and snapshots, ECR repositories/images, and
  CloudWatch log groups;
- VPC endpoints, load balancers, ECS clusters/services/tasks, SQS queues, ACM
  certificates, Route 53/DNS resources, and any other account resources tagged
  or named for the application; and
- untagged or incorrectly tagged resources that a tag-only inventory would
  miss.

For every item, retain the account and Region, service, physical identifier,
tags, creation time, last observed use, storage/quantity, estimated ongoing
cost, owner, retention reason, decision, approval reference, and deletion or
next-review date. Each control resource has the nine required ResourceTags
`application`, `environment`, `control-scope`, `owner`, `finance-owner`,
`cost-center`, `managed-by`, `ticket`, and `approval-record`; values remain
unapproved until the control record is approved. The CloudFormation stack and
change set also carry a tenth stack-only tag,
`control-configuration-sha256`, which binds those stable settings without
binding mutable delivery evidence into create-only resource tags.

The Resource Groups Tagging API `GetResources` does not return untagged
resources, so it cannot be the sole inventory source. See
[GetResources API behavior](https://docs.aws.amazon.com/resourcegroupstagging/latest/APIReference/API_GetResources.html).
Every inventory query is itself an AWS call and requires authorization. A
retained resource stays owned and potentially billable until an authorized
deletion is verified; stack deletion is not cleanup evidence.

## Evidence and acceptance boundary

| Evidence                                                          | Local result now  | Authorized live requirement                    |
| ----------------------------------------------------------------- | ----------------- | ---------------------------------------------- |
| Record shape and example sentinel state                           | Checkable locally | Approved record must pass semantic validation  |
| Account, alias, role, and Regions                                 | `NOT_RUN`         | Independent verification `PASS`                |
| Warning delivery                                                  | `NOT_RUN`         | Confirmed recipient delivery `PASS`            |
| Critical delivery                                                 | `NOT_RUN`         | Confirmed recipient delivery `PASS`            |
| Anomaly delivery                                                  | `NOT_RUN`         | `PASS`, or `NOT_APPLICABLE` only when disabled |
| Daily retained-resource review                                    | `NOT_RUN`         | Complete service-native inventory `PASS`       |
| KAN-34 cloud validation, migration, health, rollback, and cleanup | `NOT_RUN`         | Separately authorized application evidence     |

Local tests can prove fail-closed parsing, record integrity, template structure,
and zero default AWS calls. They cannot prove account identity, current account
configuration, notification receipt, current prices, deployment success,
resource cleanup, or zero spend. KAN-229 live acceptance therefore remains
**Not Run** until the authorized account phase is completed and independently
verified.
