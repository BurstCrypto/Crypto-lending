# KAN-173: normalized yield opportunity and discovery adapter contracts

KAN-173 defines the local, provider-neutral boundary for Smart Yield discovery.
It does not select or approve a provider or protocol, fetch market data, open a
provider account, enable external egress, persist a catalog, or authorize an
investment. No live adapter is included.

## Version 1 contracts

The authoritative TypeScript boundary is exported from `apps/api/src/yield`.
Both contracts have independent literal versions so a caller can reject an
incompatible adapter or opportunity before interpreting its data:

| Contract               | Version marker                         | Version 1 type                 |
| ---------------------- | -------------------------------------- | ------------------------------ |
| Normalized opportunity | `YIELD_OPPORTUNITY_SCHEMA_VERSION = 1` | `NormalizedYieldOpportunityV1` |
| Discovery adapter      | `YIELD_DISCOVERY_ADAPTER_VERSION = 1`  | `YieldDiscoveryAdapterV1`      |

An adapter exposes its adapter and opportunity-schema versions and returns only
normalized opportunities. A raw provider record cannot cross
`YieldDiscoveryAdapterV1.discover`. The polling application supplies a trusted
canonical `requestedAt` and an optional opaque cursor; the page returns the
provider identifier, discovery timestamp, next cursor, and immutable normalized
records.

`normalizeYieldOpportunityV1` is the runtime schema boundary. It validates,
copies, and deeply freezes these required sections:

- stable opportunity, provider, protocol, and protocol-market identifiers;
- exact chain identifier and case-sensitive asset contract or mint, symbol, and
  asset decimals;
- APY, TVL, utilization, and immediately available exit liquidity with source
  timestamps;
- explicitly reported or not-reported fee and limit disclosures;
- deposit/withdrawal availability, status, timestamp, and reason codes; and
- source kind, record/reference identifiers, source and retrieval timestamps,
  exact-payload SHA-256, normalizer identity/version, and unique provider
  provenance attributes.

Unknown or accessor-backed fields, malformed timestamps, duplicate provenance
keys, invalid enum values, noncanonical exact decimals, negative amounts,
utilization outside `[0, 1]`, and non-lowercase payload digests fail closed with
a stable `YieldOpportunityValidationError` code. Provider identifiers and asset
contracts are retained case-sensitively; this contract does not silently infer
or relabel either one from a ticker.

## Decimal representation

Every financial value uses `YieldDecimalV1`:

```text
value = mantissa * 10^-scale
```

`mantissa` is a canonical signed base-10 integer string and `scale` is a bounded
integer. This representation is JSON-safe and preserves trailing fractional
precision without converting through an IEEE-754 number. APY, utilization, and
rate fees are ratios: `0.0525` means 5.25 percent. Monetary amounts declare
whether they are denominated in the opportunity asset or USD.

Provider normalizers can use `yieldDecimalFromString` for exact decimal text and
`divideYieldDecimalByPowerOfTen` for exact unit shifts. Examples include dividing
basis points by `10^4`, ppm by `10^6`, micro-USD by `10^6`, and token atomics by
the asset's decimal power. Exponent notation and JavaScript numbers are rejected
at this boundary because their source precision cannot be proven.

## Provenance boundary

Economic fields promoted into the normalized schema retain their own exact
values and timestamps. `provenance` separately binds the result to the source
record/reference and SHA-256 of the exact pre-normalization payload. Unique
string attributes retain provider-specific sequence, block/log, query, status,
or similar source identifiers without placing a raw provider payload in the
catalog contract.

An adapter must compute `payloadSha256` over the exact bytes it received before
parsing. A reserialized object is not interchangeable with those original bytes
in a live implementation. Provenance describes the observation; it does not
prove that a provider response came from the configured chain, that the data is
fresh enough to execute, or that the opportunity is approved. Later ingestion,
chain-verification, risk, eligibility, and execution tickets must enforce those
controls independently.

## Contract fixtures

The focused contract suite implements two local-only fixture adapters:

- a decimal-string API shape with APY ratios, percentage utilization, decimal
  USD/asset amounts, named fees, deposit bounds, response sequence, and endpoint
  provenance; and
- an on-chain/indexer shape with APY basis points, utilization ppm, micro-USD,
  token atomics, block/log/query provenance, and limited withdrawals.

The tests reconstruct the exact normalized decimal strings—including values
beyond JavaScript's safe integer and decimal precision—and assert preservation
of provider/protocol, asset contract, chain, timestamps, fees, limits,
availability, payload digest, and provider-specific source identifiers. The
fixtures make no network call.
