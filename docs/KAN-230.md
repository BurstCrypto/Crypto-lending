# KAN-230: ACM certificate and DNS readiness

KAN-230 owns the application hostname, public-certificate, authoritative-DNS,
cutover, renewal, and rollback prerequisites that sit outside the KAN-34
application stack. Repository work is deliberately **local only**. No AWS,
registrar, DNS-provider, DNS-resolution, TLS, certificate-transparency, or
pricing API is called by the validator, plan renderer, or CI.

No certificate, domain, hosted zone, DNS record, private CA, monitoring target,
load balancer, trial, subscription, or paid service has been created for this
ticket. All live evidence remains `NOT_RUN`.

## Current no-additional-charge policy

The only supported certificate path is an ACM-issued, non-exportable public
certificate used by an ACM-integrated Application Load Balancer. AWS currently
lists that certificate mode at no additional charge. The approved path must use
an existing authoritative public DNS zone and an already owned parent domain.

The control record permanently keeps these alternatives `NOT_AUTHORIZED` under
the current policy:

- registering or renewing a new domain;
- creating a Route 53 hosted zone;
- requesting an exportable ACM certificate;
- creating or using ACM Private CA; and
- activating paid certificate/DNS monitoring.

An imported certificate is deliberately deferred. Import requires a separately
reviewed external-CA cost and renewal decision plus handling private-key
material outside the repository and command line. The current package never
accepts private keys, PEM, provider tokens, email addresses, or credentials.

Pricing references must be refreshed before authorization:

- <https://aws.amazon.com/certificate-manager/pricing/>
- <https://aws.amazon.com/route53/pricing/>

`estimatedMonthlyIncrementUsd: "0.00"` means only that the selected certificate
and existing-DNS change have no newly approved service fee. It does not make the
KAN-34 load balancer or application environment free.

## Versioned local contract

The inert example is
[`infra/aws/acm-dns-control-record.example.json`](../infra/aws/acm-dns-control-record.example.json),
with its strict JSON Schema beside it. Never convert that tracked example into
an operational record. Copy it to a git-ignored filename ending in
`.acm-dns.local.json` in the approved local controls directory outside the
repository. Repository validation rejects operational records even when Git
would ignore them.

The record binds:

- exact AWS partition, account, role, and load-balancer Region;
- one lowercase non-production application hostname beneath an approved parent
  domain;
- authoritative DNS provider, existing-zone reference, ownership evidence, and
  record type;
- non-exportable ACM mode, DNS validation, exact certificate ARN and SANs,
  issued status, expiry, fingerprint, managed-renewal method, threshold, and
  owner;
- exact ALB ARN, DNS name, canonical hosted-zone ID, proposed/prior DNS values,
  provider-controlled CNAME TTL (or `NOT_APPLICABLE` for a Route 53 ALB alias),
  and rollback deadline;
- current zero-increment pricing decision and the explicitly unauthorized paid
  alternatives;
- certificate, DNS-change, cutover, and rollback approver roles; and
- an independent verifier who cannot also be one of those approvers.

Operational references are identifiers or links to protected evidence—not raw
responses, personal addresses, DNS validation tokens, or secrets.

The validator accepts the control record only as a canonical, non-empty,
single-link regular file whose contents remain stable across two bounded reads.
The 32 KiB (32,768-byte) limit is deliberately generous for this small contract
while bounding local memory and review scope. Input must be strict UTF-8 JSON
without a byte-order mark or duplicate object keys at any nesting depth;
directories, symbolic links, hard links, malformed text, ambiguous JSON, and
files that change during inspection fail closed behind one path-free error.

## Fail-closed lifecycle

The record has four semantic stages. One broad approval cannot authorize every
mutation:

1. `authorization` approves only a future request for the selected
   non-exportable certificate and its DNS validation record. Certificate, ALB,
   application DNS, and live evidence fields must remain `NOT_RUN`.
2. `bootstrap` requires independently checked hostname ownership, an `ISSUED`
   certificate in the exact account/Region, exact SAN coverage, a future expiry,
   fingerprint, and completed DNS validation. Application DNS and ALB fields
   remain `NOT_RUN`. This is the minimum KAN-230 prerequisite accepted by a
   future authorized KAN-34 Plan.
3. `cutover` additionally binds the exact healthy KAN-34 ALB and canonical zone,
   prior DNS state, cutover TTL, rollback deadline, and approval roles. It still
   cannot claim that DNS or TLS testing happened.
4. `final` requires every live DNS, TLS, redirect, unmatched-host, renewal,
   expiration-monitoring, and rollback result to be `PASS` with a UTC observation
   time and protected evidence index.

For every evidence-bearing stage, `approvedAt` and the independent verifier's
`verifiedAt` must be refreshed after the evidence observation. A prior-stage
approval cannot be reused to make later evidence appear reviewed.

The stable configuration digest excludes evolving certificate/DNS observations
and evidence. The full record digest changes as evidence matures. KAN-34 binds
both the stable KAN-230 configuration and the exact prerequisite record reviewed
for its change set.

## Local validation and plan rendering

These commands use local files and Node/PowerShell only:

```powershell
npm run infra:validate:acm-dns
npm run infra:test:acm-dns
powershell.exe -NoProfile -ExecutionPolicy Bypass -File infra/aws/test-invoke-acm-dns-local.ps1
```

The entry point defaults to validating the inert example:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File infra/aws/invoke-acm-dns-local.ps1
```

After owners fill and approve a private operational record, a local-only plan
may be rendered. The plan is non-executable, contains explicit prohibitions, and
must use the ignored `.acm-dns-plan.local.json` suffix. This is not permission to
perform any listed future step.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass `
  -File infra/aws/invoke-acm-dns-local.ps1 `
  -Action RenderPlan `
  -Mode authorization `
  -RecordFile C:\approved-controls\staging.acm-dns.local.json `
  -ExpectedAccount 123456789012 `
  -ExpectedRegion us-west-2 `
  -OutputFile C:\approved-controls\staging.authorization.acm-dns-plan.local.json
```

The script intentionally has no cloud, DNS, TLS, or provider execution action.
Each run reports zero AWS calls, DNS queries, TLS connections, provider calls,
resources, and paid activations.

## KAN-34 integration

The application template continues to consume `AlbCertificateArn` and
`ApplicationHostname`; it does not create ACM, Route 53, private-CA, custom, or
provider resources. The KAN-34 guard now requires an ignored KAN-230 record for
Plan and Deploy, validates it before AWS CLI discovery, matches both inputs, and
binds its record/configuration digests into the reviewed change set.

The load balancer exposes its ARN, DNS name, and canonical hosted-zone ID for a
future controlled cutover record. Both HTTP and HTTPS listeners now return a
fixed 404 for unmatched hosts. Only the approved hostname receives the HTTP 301
redirect or application forwarding. HTTPS uses the reviewed TLS 1.2/1.3 policy.

## Separately authorized future runbook

The following phases describe responsibilities; they are not executable cloud
instructions and have not been run:

1. Domain/DNS owners verify the exact existing parent domain and authoritative
   provider, current costs, access roles, and renewal responsibility.
2. Certificate-request and independent approvers review the `authorization`
   digest. A separately authorized operator requests only the selected
   non-exportable public certificate in the ALB Region.
3. The DNS owner publishes only the ACM validation record in the approved
   existing zone. It must remain present for managed renewal.
4. An independent verifier records exact SANs, status, expiry, fingerprint, ARN,
   account, Region, and DNS-validation evidence in a `bootstrap` record.
5. After an authorized zero-count KAN-34 deployment and healthy ALB evidence,
   owners snapshot the prior DNS state and approve a `cutover` record.
6. The DNS owner changes only the approved application-hostname record to the
   exact ALB target. No domain, hosted zone, health check, or unrelated record is
   created.
7. A clean independent client verifies DNS exclusivity, chain, hostname, HTTP
   redirect, HTTPS health, mismatch/expired/HTTP-only failure, and unmatched-host
   rejection. Evidence must not contain cookies, authorization headers, tokens,
   customer data, or private keys.
8. The team tests rollback to the captured prior value (or safe record removal),
   confirms propagation, restores the reviewed target if approved, and verifies
   renewal/expiration ownership and alert delivery.

Any failed observation stops advancement. The old certificate and DNS target
must not be removed until the new path and rollback are independently verified.
