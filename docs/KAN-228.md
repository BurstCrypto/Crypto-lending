# KAN-228: Application container artifacts

Status: **LOCAL BUILD AND INTEGRATION VALIDATED; PUBLICATION NOT RUN**

KAN-228 is being worked under the repository's zero-spend boundary. Local Docker
builds, local ephemeral evidence, and tests against the already-running Compose
services are allowed. Registry login, Docker Scout, ECR or other registry pushes,
AWS/cloud APIs, hosted CI, signing services, and paid scanners were not used.

## Implemented controls

- API, worker, and web builds use a literal digest-pinned Node 22.23.2 base. The
  official 2,407,857-byte npm 11.6.4 tarball is pinned by SHA-256, checked again
  before extraction (`9c07edca12853cddbf4fed4e372485aa60c064f9bf3e4cd157a2db5518a1792b`),
  and installed at a fixed path. Dependency installs use the lockfile, disable
  lifecycle scripts, audit, and funding calls, and application build layers run
  with BuildKit network access disabled.
- Clean builds use a temporary Git-archive context for the requested revision,
  so ignored or untracked files under an allowed source directory cannot enter
  an image. The checked-in `.dockerignore` remains an exact deny-all allowlist.
- The reviewed Dockerfiles are bound by canonical SHA-256 values. Appending an
  unchecked remote `ADD`, privileged `RUN`, alternate user, command, entrypoint,
  or mutable build input fails static policy validation.
- Runtime targets use UID:GID `10001:10001`. The backend explicitly creates the
  RDS trust-store parent with traversable root-owned permissions before adding
  the checksum-pinned, read-only CA bundle.
- A clean build emits local BuildKit `mode=max` provenance and verifies its
  target, source revision, platform, image descriptor digest, and exact
  base/npm/CA materials before deleting the temporary metadata file.
- The installed npm CLI produces in-memory CycloneDX 1.5 production-dependency
  SBOMs for the API/worker closure and web closure. The harness validates the npm
  version and dependency graph, reports normalized hashes, and persists no
  generated artifacts in the repository.
- A standalone smoke or integration run requires all three explicit image
  descriptor digests and a clean checkout; a mutable short tag plus a copied OCI
  label is insufficient.
- File, Node version, UID, build ID, and CA checks execute in both backend tags
  where applicable. API and web liveness smoke runs with no network, a read-only
  root, a bounded `tmpfs`, all capabilities dropped, `no-new-privileges`, and a
  PID limit.
- The local infrastructure path creates a UUID-named internal-only Docker
  network, isolated PostgreSQL database, isolated tagged LocalStack queues, and
  isolated Redis prefix. It runs migration `up` then `verify` from the exact API
  image, checks API PostgreSQL/Redis/SQS readiness, starts the exact worker image,
  executes its health command, and requires Docker health status `healthy`.
- Temporary containers, queues, database, and network carry per-run ownership
  markers and are removed only after those markers are verified. Existing
  Compose containers are connected additively and are never restarted.

Local integration intentionally uses nonproduction plaintext PostgreSQL and
Redis connections because the checked-in local services do not terminate TLS.
That traffic is limited to the internal Docker network. The separate
production-mode network-none smoke retains `verify-full`, `rediss://`, and
canonical HTTPS SQS configuration.

The first runtime probe found and then reproduced a real issue: the remote CA
`ADD` had created `/etc/ssl` without directory execute bits, so non-root Node
could not read its OpenSSL configuration. Explicit `0755` parent creation fixed
the issue without relaxing the runtime user or sandbox.

## Remaining gates

The installed Docker/buildx/npm toolchain can produce useful BuildKit provenance
and npm dependency SBOM evidence without a login. It cannot currently produce a
reviewed whole-image/OS SBOM or vulnerability report: Syft, Trivy, Grype, and
Cosign are not installed, and Docker Scout is explicitly prohibited for this
zero-spend run. npm SBOMs do not describe Debian/base-image packages or the full
filesystem.

No image was published, signed, or pulled back by digest. ECR repository policy,
immutable retention, registry scanning, signatures, whole-image SBOM,
vulnerability disposition, and deploy-time digest verification remain open.
The exact worker image was started and dependency-health checked, but this batch
did not seed and assert an end-to-end outbox publication from that image.
KAN-54 remains the broader vulnerability-scanning dependency. These local tags
and unsigned ephemeral evidence must not be treated as releasable artifacts or
proof of hosted provenance.
