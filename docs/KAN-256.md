# KAN-256: zero-egress local EVM development chain

Status: `LOCAL_IMPLEMENTATION_COMPLETE`

KAN-256 adds a cost-free, loopback-only EVM development chain and connects it
to the existing stablecoin balance indexing, synchronization, and local-demo
portfolio path. The implementation uses pinned `hardhat@3.14.0` with its EDR
simulated L1 engine, no configured accounts, no Solidity compilation, and no
signed, public-network, or real-asset transaction submission. Fixture balance
changes are real zero-fee transactions mined only by the local child.

The runtime is a real local EVM state-transition and block-production boundary,
not a mocked JSON-RPC response. It is not a decentralized or proof-of-stake
validator and does not claim public-testnet, consensus, finality, or production
evidence.

## Exact local product proof

`npm run test:local-evm` starts an actual Hardhat child on Windows, verifies
there are no RPC accounts, checks the exact installed contract bytecode, reads
seeded storage with `eth_call`, performs authenticated reset and balance-control
requests, runs the API product probe, and tears down both the supervisor and its
child. Reset is a full child restart; no runtime path reads or trusts EVM
snapshot metadata. Adversarial lifecycle coverage proves that unrelated or
reused PIDs are never signaled, missing ownership with a matching endpoint
fails closed, and stale state is removed only when both fixed endpoints are
absent. It also overlaps an admitted reset with graceful supervisor shutdown to
prove control admission drains before final child teardown, then force-kills
the supervisor during a delayed reset to prove the operating-system IPC tether
closes both loopback endpoints. The resulting exact stale record is recoverable,
and the next authenticated start succeeds.

The real mutation regression captures an explicit block tag, changes the wallet
balance using a mined local transaction, and proves that the earlier block hash,
code, and balance remain unchanged. The product probe composes the real EVM
indexer, balance-sync orchestrator, portfolio aggregation, and buying-power
classes.

The local-demo launcher injects the live per-launch values as
`LOCAL_EVM_CONTROL_LAUNCH_ID` and `LOCAL_EVM_CONTROL_CAPABILITY` into the API
child. API state initialization uses only the authenticated loopback control
channel. Authenticated control results carry a random per-child instance ID;
the API brackets seeding and synchronization with it and commits its wallet
cache only after same-instance validation. Its read path verifies the exact
mock-USDC bytecode at the pinned tag, performs the pinned call, and rechecks both
the code and block afterward.

The web client uses a separate local-demo response adapter and renderer that
accept exactly `eip155:31337` plus mock USDC
`0x0000000000000000000000000000000000000101`. Wallet registration projections
remain Sepolia/devnet-shaped, and the shared production parser, renderer,
network allowlist, and asset allowlist do not acquire the LOCAL identity.

The authenticated API e2e test separately passes the real session guard and
HTTP controller, changes its injected chain balance after the initial request,
and verifies that the next response contains the new amount and a different
snapshot ID. Together, these tests cover the real-chain adapter and the
authenticated product boundary without making a public request.

## Remaining non-local gates

No local work remains for the development-chain objective. This result does
not satisfy any future requirement for public testnet operation, peer/validator
consensus, production persistence, live provider behavior, market-price
evidence, Solana chain integration, or financial authorization. Each requires
separate scope and approval; none is silently substituted here.
