# KAN-231: Controlled outbound application egress

KAN-231 prepares the decision and local controls for external application
egress under KAN-34. It does **not** activate egress. The current interim state
is `NO_EXTERNAL_EGRESS`: no external hostname is approved and no application
workload is allowed to reach a public RPC, indexer, identity, oracle, pricing,
or other vendor endpoint.

The governing [ADR 0002](adr/0002-controlled-external-egress.md) remains
**Proposed**. No future paid architecture has been selected. Local work on this
ticket makes no AWS, DNS, TLS, provider, Marketplace, subscription, or vendor
signup call and creates no resource, trial, or paid service.

## Dependency boundary

| Ticket | Dependency role                                                                   | KAN-231 consequence                                                                                                                                                                                      |
| ------ | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| KAN-34 | Root `applicationBaseline` dependency                                             | An `approved` or `final` policy requires an approved KAN-34 decision reference. The committed example remains `NOT_APPROVED` and does not claim that a live baseline exists.                             |
| KAN-37 | **Integrate authentication and secure sessions** — local implementation in review | A provider-neutral local boundary exists, but no identity provider, callback/issuer host, token audience, redirect, credential flow, or availability policy is approved.                                 |
| KAN-62 | **Select RPC and indexing providers** — local proposal prepared                   | Alchemy and QuickNode are proposed as distinct provider candidates, but KAN-251 approval/live validation is pending and no plan, endpoint host, region, SLA, API key, egress path, or spend is approved. |

Accordingly, the committed example policy must have an empty destination list,
all three root dependency approvals set to `NOT_APPROVED`, ADR approval unset,
`approvedAt`, `acceptedAt`, `expiresAt`, and every evidence binding set to
`NOT_RUN`, and `NO_EXTERNAL_EGRESS` as both the current mode and selected
control. Do not add a plausible vendor hostname as a placeholder; examples have
a habit of becoming accidental production configuration.

The current KAN-34 template declares no NAT gateway or general internet route
for its private tasks. The local topology policy preserves that repository
boundary; it is not a statement about deployed resources. Its possible private
AWS endpoints are platform dependencies, not approval for external application
traffic, and deploying those endpoints would itself require cost and cloud
authorization.

Browser-originated wallet, RPC, or identity traffic is outside the VPC. A
future external browser allow needs exact SDK configuration and origins. The
current web configuration installs one composed CSP on every route and the
restricted wallet lab. Production, unknown, and unset runtimes use
`default-src 'self'`, `connect-src 'self'`, and
`script-src 'self' 'unsafe-inline'`; styles remain same-origin with the reviewed
inline exception, images/fonts/media/workers allow only same-origin plus the
listed `data:`/`blob:` cases, forms and manifests are same-origin, and frames,
embedding, base changes, and objects are denied. Only explicit `development`
and `test` runtimes add loopback WebSockets and the local framework's
`'unsafe-eval'` script exception. This is a local static browser deny, not
live-header, extension, provider, or server-runtime evidence; CSP cannot enforce
backend egress.

## Local policy artifacts

The KAN-231 policy set is intentionally declarative:

- `infra/egress/egress-policy.example.json` is an inert, secret-free
  `NO_EXTERNAL_EGRESS` record;
- `infra/egress/egress-policy.schema.json` defines the exact record shape;
- `infra/egress/validate-egress-policy.mjs` applies semantic checks that JSON
  Schema alone cannot express; and
- `infra/egress/validate-egress-policy.test.mjs` exercises
  `example`/`proposed`/`approved`/`final` state transitions and unsafe mutations
  without making network calls.

The record produces `canonicalSha256` over every field and
`policyConfigurationSha256` over the authorized technical, dependency, cost,
and design-approval configuration. Final
`evidence.policyConfigurationSha256` must equal that configuration digest, and
`evidenceIndexReference` must begin with
`evidence-index:KAN-231:<that-hash>:`. An unchanged design deliberately keeps
the same configuration digest from `APPROVED` through post-evidence
`ACCEPTED`, so runtime evidence stays bound to the pre-activation design. The
full canonical digest changes when lifecycle, evidence, or acceptance metadata
changes.

The configuration digest includes `schemaVersion`, `policyId`, `currentMode`,
`approvedAt`, expiry, environment, dependencies, architecture, design
approvers/decision/verification, and destination configuration. It excludes
root `status`, `acceptedAt`, `authority.acceptanceVerifier`,
`authority.acceptanceDecision`, all evidence fields, and destination
kill-switch test time/evidence. Those excluded values remain covered by the
full canonical digest. Any change to an included configuration field requires
review and a newly bound configuration digest. Neither digest approves the
contents, confers IAM authority, proves a reference exists, or permits a cloud
action.

### Required root fields

The root record contains `schemaVersion`, `status`, `policyId`, `currentMode`,
`approvedAt`, `acceptedAt`, `expiresAt`, `environment`, `dependencies`,
`architecture`, `authority`, `destinations`, and `evidence`. `environment` binds
`application`, environment `name`, `accountId`, `applicationRegion`, and
`sourceRevision`. `dependencies` has `applicationBaseline`,
`authenticationSessions`, and `rpcIndexing`; each binds `ticket`,
`approvalStatus`, and `decisionReference`.

`architecture` records `adrStatus`, `decisionReference`, `selectedControl`,
`defaultAction`, `dnsPolicy`, `ecsBoundary`, `browserBoundary`, `killSwitch`,
the three aggregate monthly cost fields, `costDecision`,
`activationAuthorization`, `financeApprovalReference`,
`billingControlRecordReference`, `billingControlConfigurationSha256`,
`pricingAsOf`, and `pricingExpiresAt`. `authority` records
`architectureApprovers`, `securityApprovers`, `privacyApprovers`,
`financeApprovers`, `independentVerifier`, design `decision`, `verifiedAt`, and
the separate post-evidence `acceptanceVerifier` and `acceptanceDecision`.
`evidence` records `localPolicyValidation`, `unlistedDestinationDenied`,
`allowedDestinationReached`, `providerOutage`, `dnsFailure`, `tlsFailure`,
`logsRedacted`, `killSwitch`, `observedAtUtc`, `evidenceIndexReference`, and
`policyConfigurationSha256`.
Logging rules, owners, costs, expiry, and destination kill switches are scoped
per destination rather than hidden in a global wildcard. Unknown fields are
rejected so a misspelling cannot silently bypass review.

The fixed architecture invariants are `defaultAction: DENY`,
`dnsPolicy: DENY_UNLISTED_AND_UNAPPROVED_PRIVATE_ADDRESSES`,
`ecsBoundary: PRIVATE_SUBNETS_NO_PUBLIC_IP_NO_DEFAULT_INTERNET_ROUTE`,
`browserBoundary: OUTSIDE_VPC_ENFORCE_WITH_CSP_AND_APPLICATION_ALLOWLIST`, and
`killSwitch: DISABLE_ALL_EXTERNAL_EGRESS`. Selectable controls are limited to
`NO_EXTERNAL_EGRESS`, `BROWSER_APPLICATION_CONTROLS_ONLY`, `PRIVATE_ENDPOINTS`,
`EGRESS_PROXY_WITH_NAT`, and `NETWORK_FIREWALL_WITH_NAT`. An approved ECS
destination requires one of the last three and a matching `vpc-endpoint:`,
`egress-proxy:`, or `network-firewall:` reference; browser-only controls cannot
authorize an ECS destination.

The billing fields bind an approved operational policy to KAN-229's reviewed,
unexpired control record and exact configuration digest. `approved` and `final`
CLI validation requires `--billing-control-record` pointing to a regular,
non-symlink final KAN-229 record outside the repository. It locally validates
that record for the same environment/account/Region, exact KAN-229 identity,
configuration digest, and expiry. It makes no AWS call and cannot independently
prove that the record's claimed live controls still exist.

The repository currently contains only the inert example, and this ADR remains
Proposed. No `approved` or `final` operational record or live evidence exists.

### Destination fields

Every future destination is a separate caller/service allow and includes:

- stable `id`, `status`, `dependencyTicket`,
  `dependencyDecisionReference`, `service`, `purpose`, `approvedApiScope`,
  `credentialReference`, and `reviewExpiresAt` values;
- `serviceAccess` with the caller runtime (`web-browser`, `web-server`, `api`,
  `outbox-worker`, or `migration-task`), browser/ECS execution boundary,
  service-specific `identityReference`, exact `networkControlReference`, and a
  prohibition on borrowing another service's allow;
- `endpoint`, `dns`, and `tls` objects with the exact hostname, HTTPS/WSS
  scheme, port, redirects, resolution/failure policy, SNI, TLS minimum,
  certificate validation, and invalid-certificate prohibition;
- `owners` for the provider and service, security, privacy, finance, and
  availability decisions, plus `data` classifications and credential transport;
- `resilience`, `fallback`, and `killSwitch` objects for timeout, bounded
  retry/jitter, circuit breaker, degraded/outage behavior, an exact compatible
  approved alternate or no alternate, and immediate destination denial;
- `logging` allowed metadata, mandatory redactions, disabled body/query logging,
  retention and alert owner, plus kill-switch activation/test evidence;
- `monitoring` status, selected metrics, explicit threshold rules, owner, alarm
  references, and its own cost/activation/pricing contract; and
- a separate destination `cost` decision and expiry, with the architecture cost
  envelope and independent review applying to the complete policy.

`IDENTITY` entries bind to KAN-37. `RPC` and `INDEXING` entries bind to KAN-62.
`ORACLE`, `PRICING`, `WALLET_VENDOR`, and `PARTNER_API` entries require a
separate concrete downstream KAN ticket; KAN-37, KAN-62, and KAN-231 cannot be
reused as their provider decision. KAN-34 is likewise the root application
baseline, not a downstream provider decision. Each approved fixed-category destination's
`dependencyDecisionReference` must equal its root dependency decision.

Wildcards, literal IPs, user information in URLs, credentials or tokens, query
strings, HTTP downgrade, ports other than 443, loopback/link-local or
unapproved private destinations, unlisted redirects, unlimited retries,
unapproved fallbacks, and secret-shaped logging fields fail validation. An
`EXACT_HOST_ALLOWLIST` redirect must resolve to exactly one other approved,
compatible destination record and must never forward credentials. A
`USE_APPROVED_ALTERNATE` fallback must name another listed approved destination.
Both relationships preserve scheme/port, the complete execution identity and
network control, service, dependency ticket/decision, data classifications,
credential reference, TLS, DNS, and API scope. Redirect-only, fallback-only,
and mixed redirect/fallback cycles all fail validation.

The recursive safety scan rejects private keys, AWS/Slack/GitHub/OpenAI tokens,
JWTs, bearer values, secret assignments, credentials embedded in URIs, email
addresses, literal EVM addresses, SSNs, and phone numbers anywhere in the
policy. Public IP-shaped values are also rejected in narrative/reference
fields while exact structured endpoint validation handles address fields.
Operational names use non-personal role aliases and opaque references;
personal contact data and credential values belong in separately protected
systems, not this record.

Each destination's monitoring contract selects 1–6 of
`egress_request_total`, `egress_failure_total`, `egress_latency_ms`,
`egress_denied_total`, `circuit_breaker_open`, and
`egress_kill_switch_active`. It defines 1–12 unique alert rules so every selected
metric has a threshold, comparison, evaluation count, supported period,
missing-data behavior, and—only after approval—an exact `alarm-ref:` reference.
Monitoring has a named owner and a separate bounded cost contract; it is
`PROPOSED` with unapproved costs before design approval and `APPROVED` with
approved costs/activation for `approved` and `final` modes.

## Required runtime behavior for a future design

### Exact caller and destination

Each runtime gets only its own reviewed allows. The API, web server, worker,
and migration task may not share an unrestricted NAT route or rely on a common
credential as identity. Destination enforcement must combine the strongest
available service identity, task role, security group, proxy policy, exact DNS
hostname/SNI, scheme, port, and application configuration. A provider CIDR by
itself is not identity.

Browser connections have their own origin/SDK/CSP manifest and evidence. They
remain separate from server controls even if both use the same vendor.

### DNS, TLS, and redirects

- Use the selected resolver path and record how DNS failure, new answers,
  rebinding, TTL expiry, and private/loopback/link-local answers are handled.
- Require TLS 1.2 or newer, exact SNI/hostname verification, a valid system trust
  chain, and normal certificate validity checks. Never disable verification to
  recover from an outage.
- Disable TLS interception unless a separate threat model, privacy review,
  trust-store lifecycle, and failure test are approved.
- Disable redirects by default. A required redirect is a second exact,
  compatible destination record; HTTPS downgrade, alternate ports, credential
  forwarding, unexpected hostnames, redirect cycles, and SDK fallback URLs are
  denied.

### Failure, fallback, and kill switches

Use bounded timeouts, at most five attempts with exponential jitter, never retry
non-idempotent requests, and a bounded fail-closed circuit breaker. An outage
may disable only the dependent feature, return a clear retryable response,
serve approved-age non-sensitive stale data, or stop the affected worker. It
may not fall back to an unlisted provider, public RPC, literal IP, or SDK
default. The only alternate-provider path is an explicitly listed and approved
compatible destination; service borrowing and fallback cycles are prohibited.

Provide independently operable kill switches for one destination, one caller,
and all external application egress. The switch defaults to deny, takes effect
within a documented maximum time, is observable without exposing secrets, and
can be rolled back to the exact approved policy digest. Emergency disablement
is allowed; re-enablement requires approval.

### Logs and redaction

The manifest allows only the selected subset of `destinationId`, `outcome`,
`durationMs`, `statusClass`, `retryCount`, and `circuitState`. Body and query
logging are disabled, and secret fields are dropped and redacted. The redaction
list must include `authorization`, `proxy-authorization`, `cookie`,
`set-cookie`, and `x-api-key`. Retention is bounded to 1–90 days and has an
explicit alert owner.

Access, ingestion volume, alerts, and costs require approval. Test redaction
before enabling delivery; a synthetic unit result is not proof that a live log
destination received only safe fields.

## Cost gate

No KAN-231 paid control has been selected. Candidate designs can include fixed
monthly charges and usage fees for PrivateLink endpoints, NAT gateways, proxy
compute/load balancers, Network Firewall, DNS Firewall/Resolver queries,
third-party subscriptions, cross-AZ and internet transfer, log ingestion and
retention, metrics, provider APIs, licenses, support, and standby capacity.
Retries during failure can amplify several of those costs.

Before any plan, signup, trial, Marketplace action, subscription, or resource
creation, record low/expected/stress volumes, public or contract unit prices,
Region, currency, UTC price date and expiry, exclusions, fixed and variable
monthly totals, availability multiplier, cleanup tail, and owner-approved
headroom. Finance and an independent reviewer must approve the bounded design.
The `approved` policy must separately record both cost approval and activation
approval and bind the reviewed KAN-229 billing-control record/configuration
digest. A free tier, trial, credit, or `$0` certificate line item is not
activation authority.

Every destination and its monitoring contract records fixed, expected variable,
and variable-ceiling USD values with its own current pricing window and finance
reference. The architecture's three monthly envelopes must each cover the sum
of all destination and monitoring costs. `policy.expiresAt` may not outlive the
architecture price window, any destination review, any destination/monitoring
price window, or the validated KAN-229 record. Passing arithmetic does not
approve or activate a meter.

The repository-local work described here creates no cloud resource, has `$0`
incremental cloud-service cost, and leaves all usage-based meters untouched. It
does not claim that engineering work or a future live design costs nothing.
