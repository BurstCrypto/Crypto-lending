# KAN-232: PostgreSQL workload principals and rotation

KAN-232 replaces the shared PostgreSQL runtime credential with separate API,
worker, migration, ownership, and bootstrap authorities. This batch is
local-only: it changes application configuration, additive migration SQL, the
reviewed bootstrap artifact, and Docker-backed acceptance tests. It does not
call AWS, read or write a managed secret, deploy a task, or incur provider cost.

## Principal contract

| Principal                    | LOGIN | INHERIT             | Purpose                                                                                        |
| ---------------------------- | ----- | ------------------- | ---------------------------------------------------------------------------------------------- |
| `crypto_admin`               | yes   | deployment-specific | Database bootstrap owner only; never an application or migration task credential               |
| `crypto_schema_owner`        | no    | no                  | Owns the `public` application schema and every application object                              |
| `crypto_migration`           | yes   | no                  | One-off migration login; may `SET ROLE crypto_schema_owner` and nothing else                   |
| `crypto_runtime`             | no    | no                  | Inert compatibility capability required by immutable migration `0004`; its password is cleared |
| `crypto_api_runtime`         | no    | yes                 | API capability; inherits only the inert compatibility capability                               |
| `crypto_worker_runtime`      | no    | no                  | Outbox-worker capability                                                                       |
| `crypto_api_login_<slot>`    | yes   | no                  | Rotatable API A/B login; may set only `crypto_api_runtime`                                     |
| `crypto_worker_login_<slot>` | yes   | no                  | Rotatable worker A/B login; may set only `crypto_worker_runtime`                               |

Every role is `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION
NOBYPASSRLS`. Membership options and the entire direct membership graph are
verified, including `ADMIN`, `INHERIT`, and `SET` options. Capability roles are
stable and have no credential; versioned login slots can overlap during a
rollout without transferring object ownership.

`crypto_admin` is the stable RDS master username, not a rotatable A/B login.
RDS owns its generated master password and the corresponding Secrets Manager
secret, encrypted with the application data customer-managed KMS key. The
compatibility output `DatabaseCredentialsSecretArn` exposes only that managed
secret's ARN; separate IAM and KMS authorization is required before a bootstrap
operator can read it. Neither its value nor an RDS master secret selector enters
an ECS task definition.

`APPLICATION_WORKLOAD=api|worker` selects the only accepted runtime capability.
Scoped local and production database settings use the same startup-role path.
The role and `search_path=public,pg_temp` are sent as PostgreSQL wire startup
options, so no query can race ahead of role activation. PostgreSQL keeps
`pg_catalog` implicitly first. Runtime roles and logins cannot create in
`public`, cannot use database `TEMP`, and cannot set the owner or migration role.

## Capability inventory

The API can:

- read `schema_migrations`, `accounts`, and `account_profiles`;
- execute only the two reviewed `SECURITY DEFINER` account-profile functions;
- insert only `id`, `queue_name`, `payload`, and `message_attributes` into
  `job_outbox`; and
- insert only a pristine pending row through an exact row-level-security policy.

The worker can:

- read `schema_migrations` for health/readiness;
- select and delete reviewed `job_outbox` lifecycle rows; and
- update only status, retry, lock, publication, failure, and error columns under
  exact pending/published/failed row policies.

The API cannot mutate account tables or read/update/delete the outbox. The
worker cannot read account data, insert outbox work, or alter job identity,
payload, queue, or attributes. Both are denied DDL, roles, databases,
extensions, `COPY PROGRAM`, temporary objects, other schemas, other databases,
and migration `up`/`down` operations. Direct grants to a LOGIN are rejected so
`SET ROLE NONE` cannot reveal a hidden privilege path.
Verification also rejects a surviving direct session authenticated as the
schema owner, legacy capability, API capability, or worker capability, even if
that role was subsequently restored to `NOLOGIN`.

Global default privileges for `crypto_schema_owner` revoke public function
execution and type usage. Schema-scoped defaults grant no runtime or legacy
capability. Existing and future standalone types/domains are schema-owner-owned;
their ACLs and effective runtime denial are verified alongside tables,
sequences, and functions. The Docker suite creates a future function, enum, and
sequence and verifies their default ACLs. It then proves that PUBLIC type,
sequence, or column grants are detected before removing the probes.

## Checksum-safe legacy bridge

Migration `0004` is immutable and its recorded verifier recognizes
`crypto_runtime`. Migration `0005` therefore does not rewrite `0004` or its
checksum. Before bootstrap begins, an authorized operator must commit `NOLOGIN`
for every pre-existing owner/capability/legacy role, terminate every exact
owner/capability/legacy session, and verify the cluster-wide count is zero.
Bootstrap rejects a pre-existing capability LOGIN before its first mutation,
closing the reconnect window. It then clears the password verifier, removes
database authority, and retains only the exact `0004` account/profile ACL behind a
one-way membership:

```text
crypto_api_login_<slot> --SET--> crypto_api_runtime --INHERIT--> crypto_runtime
```

`crypto_runtime` cannot be set directly, cannot be a member of another role,
and cannot have any other member. It has exactly schema `USAGE`, account/profile
`SELECT`, and execution of the two reviewed functions. It is a temporary
checksum-compatibility boundary, not an accepted shared credential. It can be
removed only after a separately reviewed migration-verification evolution makes
the historical bridge unnecessary.

## Bootstrap and migration order

`infra/postgres/bootstrap-principals.sql` is the single reviewed ownership and
membership reconciliation artifact. It accepts identifiers only and never
accepts, prints, or stores passwords. Before its first mutation it verifies:

- the current database and session are owned by the supplied bootstrap role;
- all authority-bearing roles are pairwise distinct;
- API and worker prefixes are distinct and non-overlapping;
- no admin/capability role can match either LOGIN pattern;
- migration, API, and worker LOGINs already exist in the exact restricted
  shape;
- every pre-existing owner/capability/legacy role is already committed
  `NOLOGIN`; and
- every migration, owner/capability/legacy, and prefix-scoped API/worker session
  has been drained and terminated at the maintenance checkpoint.

The migration login is never created or re-enabled by bootstrap. An authorized
secret workflow must provision it and successfully authenticate it before this
artifact runs. On the pinned PostgreSQL 16 image, the portable `pg_roles` view
masks both provisioned and password-null LOGINs as `********`, so bootstrap
cannot safely distinguish them without a non-portable privileged catalog.
Actual secret authentication and SCRAM algorithm policy remain live
preflights. Bootstrap creates or reconciles only NOLOGIN capabilities, clears
every capability password, temporarily grants the bootstrap owner permission
to transfer existing `public` relations, functions, standalone types, and
domains, removes that membership, installs the exact role graph, revokes all
database privileges, and then grants only application-database `CONNECT` to
the three LOGINs.

For a fresh database, run bootstrap before `0001` through `0005`. For an
upgrade, run `0001` through `0004` with the legacy owner, stop migration and
runtime connection admission, commit `NOLOGIN` on pre-existing capability and
legacy roles, terminate all exact migration/capability/legacy and prefix-scoped
API/worker sessions, verify zero remain, run bootstrap to transfer ownership,
and then apply `0005`. The
Docker suite exercises the upgrade sequence, then rolls all five migrations
down and reapplies all five under `crypto_schema_owner`.

Every non-template database on the cluster, including the PostgreSQL
maintenance database, must revoke `PUBLIC CONNECT` before `0005`; otherwise the
effective cross-database verifier fails closed. This is a cluster bootstrap
prerequisite, not authority for the application migration to modify another
database.

## Rotation procedures

For API or worker A/B rotation:

1. Provision a new restricted SCRAM LOGIN and secret slot.
2. Grant only the matching capability with `ADMIN FALSE, INHERIT FALSE, SET
TRUE`, then grant only application-database `CONNECT`.
3. Launch replacement tasks with the new secret and require application and
   migration readiness.
4. Keep the old slot active only for the bounded overlap/rollback window.
5. To retire it, first set `NOLOGIN`, revoke capability membership and
   `CONNECT`, terminate sessions matching the exact username across every
   database, and verify zero remaining cluster sessions plus reconnect denial.
6. Drop the old login only after new tasks remain healthy. Before that drop,
   rollback restores `LOGIN`, exact membership, and `CONNECT` and replaces tasks
   again.

The Docker suite independently rehearses overlap, rollback, final revocation,
exact-session termination, old reconnect denial, and new-slot continuity for
both API and worker.

`crypto_migration` is a one-off identity, so it deliberately has no concurrent
A/B authority. Rotate it only when no migration task is running: audit and
terminate exact sessions, update the role's SCRAM verifier and authoritative
secret as one reviewed maintenance action, prove the old credential fails,
then invoke a fresh migration task with the new credential. The local suite
also rehearses rollback to the old verifier before applying the new verifier
again. This procedure is not atomic across PostgreSQL and a secret store; live
evidence must record the drain, ordering, rollback point, and post-change
authentication results.

The RDS master password has a different lifecycle. The application stack sets
`ManageMasterUserPassword: true` and binds `MasterUserSecret.KmsKeyId` to the
application data key; it does not create a second master secret, pass a master
password, or select a Secrets Manager stage or VersionId. RDS creates and owns
the secret and, by default, rotates the managed password every seven days. The
fixed-slot transition record therefore does not contain this credential and
cannot authorize, suppress, or roll back an RDS-managed rotation.

The managed value must be changed only through the RDS-managed rotation path,
not through a generic Secrets Manager value update or a custom rotation
function that could desynchronize the database and its service-owned secret.
Treat the managed secret's KMS key as an adoption and recovery binding, not a
password-rotation field. Stop on key drift; any key migration requires a
separately reviewed database/secret recovery path rather than an ordinary RDS
password rotation.

Before bootstrap or emergency ownership recovery, a separately authorized
operator must bind the current database identity, compatibility-output secret
ARN, observed managed-secret VersionId, and operation window without recording
secret bytes. The operator must ensure no other `crypto_admin` session is
active, retrieve the credential only into an ephemeral process boundary, use
verified TLS, and stop if the managed version or database identity changes.
After an automatic or separately authorized on-demand rotation, evidence must
prove new authentication, old-password reconnect denial, absence of stale
master sessions, and uninterrupted API/worker login health. Those sanitized
results belong in the nested schema-v1 `rdsMasterLifecycleEvidence` record
covered by the outer two-role-signed schema-v3 bundle. The record also binds the
exact primary database, managed secret, observed previous and current
VersionIds, compatibility output, and application/secret KMS identities. It
requires the primary database ARN/resource ID, managed-secret ARN, and
application-key ARN to equal the schema-v2 target registry's closed `rds` block;
the outer signatures also cover the v2 target digest, which includes the exact
CloudFormation stack ID.
Primary and rotated secret statuses must be `active`, with distinct
`AWSPREVIOUS` and `AWSCURRENT` VersionIds.

The lifecycle record's closed schema-v1 `supportingCapture` metadata identifies
a separately retained `RDS_MASTER_LIFECYCLE_CAPTURE` in
`SANITIZED_CANONICAL_JSON_V1` format, its `captureSha256`, and collection
timestamps. The outer signatures cover that digest. The validator checks the
metadata and digest shape but does not open the capture file, so both signing
roles must independently calculate and match the canonical capture hash before
signing. The record and capture contain no password, `SecretString`, connection,
or log material and must never be committed to Git or Jira.

An RDS-managed secret is lifecycle-coupled to its database, unlike the former
independently retained secret resource. Database deletion, replacement, or
snapshot restoration can remove or change the secret ARN and cannot be treated
as credential recovery merely because a snapshot exists. The authorized
recovery runbook must rediscover and bind the restored database's managed
secret, prove KMS access, rotate or recover the master credential as required,
and repeat positive/negative authentication checks before bootstrap authority
is used. The restored database, managed secret, VersionId, and KMS identities
and exact rebinding result belong in that same nested record. The rebound secret
must be `active` and its version `AWSCURRENT`. The closed timeline requires
capture start, access observation, rotation start/completion, restore
start/completion, capture completion, and lifecycle observation in that order,
with strict positive rotation and restore windows and a maximum 24-hour capture.

Repository/no-bundle, absent, forged, or unbranded input emits
`RDS_MASTER_LIFECYCLE_EVIDENCE_MISSING`. A malformed, already stale, or
counterfeit bundle is rejected during load/application as sanitized
`PRODUCTION_PREFLIGHT_EVIDENCE_BUNDLE_INVALID`, before any report. Evidence that
becomes stale after application restores the RDS blocker during evaluation and
can additionally fail bound public-authority revalidation with
`PUBLIC_LAUNCH_AUTHORITY_DECISION_UNVERIFIED`. The schema and blockers do not
perform the exercise; no such deployed rotation or restore drill is performed
here.

## Local verification

With the loopback Compose PostgreSQL service running:

```powershell
$env:TEST_DATABASE_URL = 'postgresql://crypto_admin:local_admin_only@127.0.0.1:5432/crypto_lending'
$env:RUN_INFRASTRUCTURE_INTEGRATION = '1'
npm run test:integration --workspace @crypto-lending/api -- database-principals.integration-spec.ts
```

The test invokes the exact checked-in bootstrap SQL through the Compose
PostgreSQL `psql` and uses UUID-scoped databases and roles, including its legacy
compatibility role. A test-only copy of immutable migration `0004` substitutes
that UUID role only inside the isolated database, so the suite never mutates
the canonical `crypto_runtime` role or membership. Cleanup terminates sessions
for each exact recorded username across the cluster and removes only recorded
test roles/databases. It also proves malicious aliased bootstrap inputs make no
role change. Before its first mutation, the suite requires both
`RUN_INFRASTRUCTURE_INTEGRATION=1` and the exact non-secret database marker,
database name, and bootstrap role installed by the Compose initializer; a
loopback URL or tunnel alone is rejected.

## Remaining live and infrastructure gates

The application baseline now composes the size-safe workload-boundary child.
API and worker receive distinct A/B database secrets, workload discriminators,
execution roles, and security groups; each execution role can read only the
phase-authorized slots for its workload. The one-off migration template accepts
only the separate `crypto_migration` secret, and no task receives the
bootstrap/master credential. The parent delegates the master password to RDS,
uses the application data key for its managed secret, and preserves
`DatabaseCredentialsSecretArn` as an ARN-only compatibility output. Property
mutation tests and offline CloudFormation lint verify only this static
composition.

CloudFormation secret creation does not create the corresponding PostgreSQL
LOGIN, install its SCRAM verifier, or prove successful authentication. The
current fixed A/B secret resources also do not regenerate merely because a
phase changes: A-to-B-to-A would select the original retained A value. The
schema-v2 transition validator enforces adjacent, append-only A/B state changes,
and the invocation guard binds each approved target to the immutable deployed
current state. Repeatable live rotation still requires the separately authorized
inactive-slot regeneration, verifier installation, candidate authentication,
task replacement, and retired-login denial evidence; none is performed by the
repository-local guard.

The child is content-addressed but has not been uploaded. Staging the exact
version in an existing versioned same-account/Region S3 bucket, planning or
deploying the nested stack, reading or updating a managed secret, and running
ECS/RDS are separately authorized actions that can incur cost.

Before live acceptance, use the authoritative secret to authenticate each new
LOGIN and independently confirm SCRAM password policy on the exact RDS
engine/version. The portable bootstrap cannot infer usable credential state
from masked `pg_roles` output; it does not depend on the superuser-only
`pg_authid` catalog and must not be weakened to create, enable, or change a
migration login.
Also record cluster-wide maintenance/other-database `PUBLIC CONNECT` posture,
service drain and task replacement, exact post-cutover session termination,
old/new authentication denial/success, RLS/default-ACL state, and break-glass
ownership recovery. Separately record the RDS-managed master secret's live KMS
readability, default seven-day rotation posture, database/secret identity,
rotation status, master-session drain, old-password denial, new-password
success, runtime-login continuity, and snapshot-restore recovery behavior in the
release- and deployment-target-bound nested schema-v1
`rdsMasterLifecycleEvidence` record and separately retained canonical capture,
whose digest is covered by the outer two-role-signed schema-v3 bundle.

PostgreSQL permits a LOGIN to change its own password and some per-role
settings. Least-privilege object grants and startup-role verification still
apply, but eliminating that residual requires an external identity/authentication
control such as a separately approved RDS IAM design. No live rotation,
Secrets Manager operation, deployment, or merge is authorized by this document.
