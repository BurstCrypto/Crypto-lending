# KAN-233: Redis ACL identities and rotation

KAN-233 replaces the application's shared Redis password boundary with named,
service-scoped ACL identities. This checked-in batch is local-only: it changes
application configuration, the local Redis fixture, validation, and Docker-backed
acceptance tests without calling AWS, creating an ElastiCache resource, reading a
managed secret, or incurring provider cost.

## Current capability inventory

Only the API uses Redis, and its only approved operation is dependency readiness
through `PING`. The outbox worker does not import Redis and its health process now
checks PostgreSQL, migration state, and SQS without constructing a Redis client.
No business cache or job-state caller currently justifies key access.

The reviewed ACL therefore grants the API lifecycle surface only:

- authenticate as one environment-bound `crypto_api_<APP_ENV>_a` or
  `crypto_api_<APP_ENV>_b` rotation slot in production;
- `PING` for readiness and `QUIT` for an orderly disconnect;
- no keys or channels; and
- `-@all` before the two explicit command grants.

The fixed `default` user is disabled. Key commands, introspection and
administration, scripts/functions/modules, transactions, pub/sub, database
selection, migration/restore, and flush operations are denied. Adding a cache
consumer requires a new capability inventory, delimiter-safe key ownership,
updated ACL validation, and new positive and cross-service negative tests.

## Application boundary

Production API configuration requires all of the following:

- `APPLICATION_WORKLOAD=api`;
- TLS with certificate verification, port 6379, and database 0;
- a named A/B ACL user and non-empty password; and
- bounded connection and command timeouts.

Production rejects the legacy `REDIS_AUTH_TOKEN`, `REDIS_KEY_PREFIX`, plaintext
transport, query/fragment overrides, process-wide TLS weakening, and credentials
for another workload. The client disables ioredis's `INFO` ready check and
`CLIENT SETINFO`, pins `tls.rejectUnauthorized=true` for `rediss://`, and exposes
only sanitized failure categories.

Production workers require `APPLICATION_WORKLOAD=worker` and reject every Redis
environment variable. The migration loader applies the same generic `REDIS_*`
rejection.

## Local rotation exercise

`infra/redis/users.acl` contains deliberately non-production fixture identities:
slot A enabled, slot B disabled, the default user disabled, and a loopback-only
test operator with no data access. The exact ordered fixture and credential
digests are pinned by `infra/redis/validate-redis-acl.mjs`.

The Docker-backed integration test uses the real application client factory and
proves:

1. anonymous, wrong-password, and disabled-standby authentication fail;
2. the active slot can perform only `PING` and `QUIT`;
3. representative data, administrative, introspection, pub/sub, scripting,
   module, and transaction commands fail;
4. A and B can overlap during a controlled cutover;
5. rollback to A works before revocation;
6. forward cutover disables A and selectively terminates its existing clients;
7. A's active and reconnecting sessions fail while B remains healthy; and
8. ACL-log assertions and application errors do not expose passwords.

The operator identity and fixture passwords are local test material, not a model
for a production application principal.

## Checked-in AWS composition

The parent application template now composes the reviewed
`application-workload-boundaries.yaml` child instead of retaining the legacy
shared Redis token, execution role, or backend security group. The child:

- creates a disabled default user and environment-bound API A/B users;
- injects only the phase-selected API username/password;
- gives the worker no Redis environment value, secret read, or port-6379 path;
- splits API and worker execution roles and task security groups; and
- exposes a disabled-by-default, no-data Redis operator identity with only the
  narrowly scoped client-termination capability. Its Redis-user password and
  one-off ECS secret injection share one exact, stage-free Secrets Manager
  VersionId after the inert schema-v3 adoption step, which also initializes the
  operator credential's singleton append-only history.

Both templates have property-complete mutation tests and pass the repository's
offline CloudFormation linter. The parent remains below the 51,200-byte direct
body limit; the child is content-addressed by SHA-256 and must be delivered only
through the separately guarded immutable nested-template path. The local work
did not create a bucket, upload an object, call CloudFormation, or deploy any of
these billable resources.

## Remaining live and design work

The local schema-v3 fixed-slot transition validator and invocation guard enforce
adjacent, current-state-bound A/B changes, immutable version histories, and
preservation of the separate Redis operator VersionId/history. The live
inactive-slot secret regeneration, Redis password installation, candidate
verification, and old-session denial actions remain separately authorized and
unperformed; the checked-in guard cannot manufacture that evidence.

The repository now provides a production-only revocation CLI and a conditional
one-off Fargate task definition. The task remains absent while
`RedisOperatorMode=DISABLED` (the default), creates no service or desired count,
uses the existing operator-only execution role and exact adopted secret
VersionId, and runs as a non-root user with a read-only root filesystem and all
Linux capabilities dropped. An omitted selector, mutable stage, alternate
version, or mixed pinned/unpinned state fails local validation. Its runtime
contract is closed to the product's Ethereum-and-Solana mainnet scope. It
accepts no command or target argument, requires an exact
single-active-slot phase (`A_ONLY` or `B_ONLY`), derives the opposite application
slot for the same deployment environment, verifies Redis TLS certificates, and
issues only `CLIENT KILL USER <inactive username> SKIPME YES`. Output contains
only the inactive slot and killed-client count; transport, host, username,
password, and raw Redis errors are never returned.

This closes the local execution-artifact design gap, not the live control gate.
No task has been authorized, registered, or run. API workload drain, an
authorized run in the intended private subnets/security group, post-command
session and reconnect denial evidence, immediate return to
`RedisOperatorMode=DISABLED`, and sanitized log/evidence review remain external.
Installing or regenerating any Redis credential also remains separately
authorized and unresolved. The A/B transition record preserves the operator
version and append-only history after adoption. A dedicated schema-v1,
two-role-signed Redis-operator artifact and guarded
`REDIS_OPERATOR_TRANSITION` path now constrain no-op chain adoption and one
exact current-to-target operator VersionId append. They bind the immutable
deployment, workload child/template, observability template, secret/KMS/user,
Redis-chain, composite credential-chain, and preserved auth/wallet-chain
identities. A transition keeps the operator disabled and its task absent,
preserves every A/B slot, and permits only the reviewed non-replacing
`RedisOperatorUser` authentication update before advancing the Redis and
composite credential chains together.

This dedicated path is still an offline/local guard. Its production authority
registry is intentionally empty, the checked-in example is `NOT_AUTHORIZED` /
`NOT_RUN`, and no operational record has been independently signed. No secret
has been staged or read, no AWS or Redis call has been made, and no operator
password has been rotated, deployed, or tested. External custody and staging,
live current-state and no-connection capture, candidate authentication,
old-credential denial, runtime continuity, forward recovery, independent
approval, and deployed execution remain production blockers.

Managed failed-authentication monitoring is now locally defined in the pinned
observability child. One alarm sums ElastiCache `AuthenticationFailures`,
`CommandAuthorizationFailures`, `KeyAuthorizationFailures`, and
`ChannelAuthorizationFailures` across the deterministic `-001` and `-002`
cache-member identities, routes ALARM and OK transitions to the explicitly
supplied topic, and exposes the same bounded metrics on the dashboard. The
template and mutation validators reject dimension, metric, aggregation, or
action drift. Actual delivery, an authorized non-production denial drill, and
sanitized response evidence remain external go-live gates.

Before deployed acceptance, an authorized non-production exercise must stage
the exact child in an existing versioned same-account/Region S3 bucket, validate
and execute the exact guarded change set, install the generated credentials into
the intended Redis users, start the exact API image, rehearse overlap/rollback/
revocation with exact resource and client identifiers, and record TLS, task
replacement, denial, log-redaction, retained-resource, and cleanup evidence.
S3 storage/requests, Secrets Manager, ElastiCache, ECS, logs, and retained
resources can incur cost, so none is authorized by this document.
