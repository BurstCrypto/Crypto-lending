# KAN-250: Authorized non-production observability acceptance

KAN-250 owns the live evidence that KAN-52 intentionally cannot produce
locally. This branch prepares the evidence contract and authorized run sequence;
it does not turn on the optional dashboard, provision or deploy infrastructure,
ingest/query telemetry, create an alarm, send a synthetic cloud request, fail a
managed job, call AWS, invoke hosted CI, or incur an approved charge.

The inert record is
[`docs/observability/kan-250-nonproduction-evidence-template.md`](observability/kan-250-nonproduction-evidence-template.md).
It remains `NOT_AUTHORIZED` / `NOT_RUN`.

## Current boundary

KAN-52's local code and static dashboard contract are merged into `main`, while
Jira remains `In Review`. The template keeps `EnableOperationalDashboard`
disabled by default and behind the existing billing acknowledgement. Local
tests can prove instrumentation contracts, bounded dimensions, synthetic trace
creation, failed-handler counters, and the declared panel/query wiring.

They cannot prove a telemetry backend exists or receives anything, a rendered
panel is correct, an IAM role is denied, an effective retention policy is
active, SQS actually redrives a message, teardown succeeded, or cost stayed
within a ceiling. In particular, `awaiting-dead-letter` is an application
transition—not evidence that the managed queue moved a message to its DLQ.

KAN-248 owns the classification, access, retention, incident-query, and audit
policy for structured application logs. Its local draft is not effective
policy. Because the KAN-52 dashboard includes structured-log queries, KAN-250
cannot query managed logs, record a log access or retention result, or receive
overall acceptance until an independently approved KAN-248 decision is bound to
its exact merged revision, packet digest, and logger-contract digest. Metrics-
or trace-only evidence cannot substitute for that gate.

## Hard gates before any external action

1. Select the exact telemetry backend and plan. Approve terms, regions,
   retention, access, data handling, quotas, overages, support, termination, and
   cleanup behavior.
2. Obtain an effective, independently approved KAN-248 decision and bind its
   exact merged Git commit and tree, governance-packet SHA-256, and logger-
   contract SHA-256. All approval conditions must be satisfied and unexpired.
   Until then, managed log queries and log access/retention acceptance are a
   hard stop, and KAN-250 cannot be accepted.
3. Approve a named non-production account/environment, exact allowed actions,
   principals, UTC window, evidence location, and incident/rollback owners.
4. Bind the exact Git/tree SHA, KAN-52 parent commit, API/web/worker image
   digests, task definitions, infrastructure template, dashboard/query
   definition, telemetry configuration, queue/DLQ, and access policy revisions.
5. Approve a cost model covering ingestion, storage through retention,
   dashboards, queries, alarms, API/KMS activity, synthetic requests/retries,
   exports, cleanup lag, retained evidence/resources, taxes, and overages.
   Name warning/stop thresholds and the person with kill authority.
6. Authorize the precise synthetic request and deliberately failed-job/redrive
   exercise. Use no real credential, customer data, wallet, or financial action.
7. Approve Security/Privacy/Operations access, redaction, retention, evidence,
   and independent verification roles. Do not reuse an implementation/evidence
   collector as the final verifier.

Parent assignment, an existing environment, a free tier, and access already
held by an operator do not satisfy these gates.

## Authorized run sequence

The following is a future runbook, not an executed action.

1. Re-run local validation on the exact candidate and verify the approved
   KAN-248 merged revision, packet digest, and logger-contract digest. Abort on
   drift, an ineffective or expired KAN-248 decision, missing stop authority, or
   an unknown cost tail.
2. Establish restricted evidence capture and UTC synchronization. Record hashes
   and safe aliases, never secrets, broad raw telemetry, or customer data.
3. Deploy the exact reviewed artifacts using the separately authorized
   environment procedure. Record actual image/task/template/config revisions.
4. Submit one approved synthetic API request while attempting spoofed inbound
   trace/request identifiers. Capture the server-generated response root.
5. Use the approved minimum query to locate the exact deployed server span and
   applicable downstream job/domain spans by that root. Record the bounded query
   hash, UTC interval, projected fields, result count, and evidence hash. Do not
   run a managed log query until the exact KAN-248 gate above is satisfied.
6. Submit one dedicated non-financial synthetic job whose handler fails by
   design. Reconcile its exact job/message identity, retry counts and timing,
   source-queue managed metrics, managed redrive, and DLQ managed metrics.
7. Prove the failure caused no financial mutation or duplicate business effect.
   Do not manually resubmit, delete, or redrive it merely to make the test pass.
8. Capture the reviewed dashboard panels for HTTP latency/errors, workload
   saturation, queue depth/age/DLQ, job failures, quote/execution lifecycle, and
   correlation traces. Bind every capture to panel/query and template hashes.
9. Verify authorized access, explicit unauthorized/cross-environment denial,
   mutation denial, access audit, effective retention, redaction, and the closed
   low-cardinality dimension vocabulary.
10. Record every failed/conditional observation with severity, owner, due date,
    disposition, and independent retest evidence.
11. Stop traffic, revoke temporary access, resolve the synthetic DLQ message
    under the approved evidence policy, remove or explicitly retain every
    temporary dashboard/alarm/export/resource, and prove kill switches/baseline.
12. Record observed and estimated-unbilled cost, retention/cleanup tail, retained
    resources, and a scheduled final billing recheck.
13. An independent verifier binds `ACCEPTED`, `CONDITIONAL`, or `REJECTED` to the
    exact revision and evidence index. Do not move the ticket based on screenshots
    or local evidence alone.

## Minimum evidence rules

- Use one environment and the smallest UTC/query scope that proves the case.
- Every structured-log query, projection, access check, retention assertion, and
  audit result must comply with the exact approved KAN-248 revision bound in the
  evidence record.
- Project only the closed KAN-52 fields; do not use wildcard fields or raw
  `@message`, headers, bodies, URLs, provider payloads, or exception text.
- A screenshot must include an evidence reference to its dashboard, panel,
  query, revision, UTC window, and underlying export hash.
- Metric label/dimension evidence must show that request, actor, account, wallet,
  job, message, intent, quote, transaction, and ledger IDs are absent.
- Absence tests use synthetic canaries stored in the restricted run record; do
  not paste canaries into Jira or this repository.
- Queue evidence distinguishes application state, source-queue metrics, actual
  managed redrive, and DLQ visibility. None substitutes for another.
- Preserve findings and audit records under approved policy; do not delete them
  during cleanup to obtain a passing result.

## Stop conditions

Stop new synthetic work and telemetry queries on unexpected spend, wrong
environment, application or KAN-248 revision drift, an ineffective or expired
KAN-248 decision, unavailable kill authority, prohibited data, unbounded/high-
cardinality dimensions, cross-environment access, missing audit, unexpected
financial mutation, queue ambiguity, or cleanup failure. Revoke temporary
access, preserve minimum finding evidence, and choose explicit rollback or
roll-forward ownership.
