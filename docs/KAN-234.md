# KAN-234: Nonproduction deployment and rollback rehearsal

Status: **IN PROGRESS — LOCAL CONTROL REHEARSAL ONLY; LIVE ACCEPTANCE NOT RUN**

KAN-234 now has an initial fail-closed evidence contract for rehearsing the
nonproduction deployment and rollback procedure without calling AWS, DNS, a
registry, hosted CI, or any other network service. This work created no cloud
resource and performed no paid operation.

The checked-in record is intentionally inert. Every execution and observation
field is `NOT_RUN`, every authorization is `NOT_APPROVED`, and validating it
does not claim a deployment or rollback occurred.

## Implemented local controls

The schema and validator require this strict sequence:

1. validate the exact account, Region, stack, source, release records, images,
   owners, evidence digests, and unexpired rehearsal window;
2. review and execute a `CREATE` change set with API, web, and worker desired
   counts fixed at zero;
3. verify database, cache, queue, private-network, and artifact readiness;
4. run separate migration apply and read-only verification tasks using the
   exact compiled production commands, task definition, image digest, task
   ARNs, and zero exit codes;
5. activate all three services only through a later `UPDATE` change set;
6. bind ECS tasks, task definitions, ALB and target health, API/web/worker and
   private-network health, the encrypted queue, and exactly one controlled
   outbox publication;
7. record publisher-worker failure injection and replacement-task recovery
   with no duplicate publication, duplicate side effect, or DLQ result;
8. redeploy the prior immutable artifact with explicit database compatibility,
   data-integrity, and post-rollback health evidence; and
9. reconcile cleanup, retained-resource owners and expiries, projected cost,
   unexpected billable resources, and blocking/high-risk findings.

Every step has a unique execution ID, evidence reference and SHA-256, UTC start
and completion time, responsible role, and evidence expiry. Steps cannot
overlap or run out of order. A missing, failed, stale, duplicated, or
secret-shaped value makes validation fail. The file loader also rejects
duplicate JSON keys, symbolic links, network/device paths, non-regular files,
and oversized records.

The local dry-rehearsal stage requires `FILESYSTEM_ONLY` and
`PROHIBITED_ZERO` for cloud, network, DNS, registry, hosted-CI, and paid
operations. It also requires a zero-dollar cost inventory and no retained
resource. A `DRY_PASS` proves only that local fixtures exercise the control
sequence; it never becomes `LIVE_PASS`.

## Local zero-cost checks

These commands read repository files and start no services:

```powershell
npm run infra:validate:rehearsal
npm run infra:test:rehearsal
```

The first command validates only
`infra/rehearsal/nonproduction-rehearsal-record.example.json`. The mutation
suite exercises a complete synthetic dry record and proves that premature
activation, failed migration verification, missing rollback/outbox/cleanup/
cost evidence, incorrect repositories or AWS identities, publisher duplicates,
stale evidence, open findings, and ambiguous JSON all fail closed.

For a future populated local record, keep the record and its referenced KAN-35
release records outside source control. Invoke the validator directly with
`--mode local-dry-run`, both local release-record paths, and every independently
supplied `--expected-*` identity/digest required by the validator. Missing or
unknown arguments fail closed. The validator only reads those files; it does
not run any command contained in a record.

## Live acceptance remains blocked

`--mode live-acceptance` currently returns `NOT_IMPLEMENTED` and fails even for
an internally consistent record. This deliberate stop prevents the initial
schema from being mistaken for deployment authorization. Before enabling that
mode, a later KAN-234 batch must compose and fully validate:

- separate approved KAN-35 records for zero-count creation, activation, and
  rollback, including each immutable change-set ARN;
- the complete KAN-229 billing control and KAN-230 ACM/DNS control plus their
  independently supplied digests;
- pre- and post-rollback task-definition, task, and image identities;
- queue-attribute evidence proving the exact queue-to-KMS-key association;
- a realistic positive live cost ceiling that accounts for billing delay; and
- resolved-finding and independent retest records with immutable bindings.

Those controls must use their canonical validators rather than shallow record
claims. A protected approval channel and independently authenticated evidence
are also still required; a JSON status, role alias, or canonical SHA-256 is not
a signature or spending authorization.

Do not call AWS, publish an image, change DNS, dispatch hosted CI, or perform a
live rehearsal because the local checks pass. No such operation was performed
for this batch.
