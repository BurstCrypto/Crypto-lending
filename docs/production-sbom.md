# Production image SBOM

Status: fail-closed CI generation and offline validation. An accepted SBOM is
an inventory of each final local runtime image; it is not a vulnerability
scan, approval, signature, provenance statement, image publication, deployment,
or mainnet authorization.

## Reviewed upstream pins (2026-09-04)

CI uses the official
[Anchore SBOM Action v0.24.2](https://github.com/anchore/sbom-action/releases/tag/v0.24.2),
published 2026-08-28, at the full commit
`3ad7283483fc7af8ff2b4ea19663c2d5ca935e26`. The reviewed
[action definition](https://github.com/anchore/sbom-action/blob/3ad7283483fc7af8ff2b4ea19663c2d5ca935e26/action.yml)
exposes independent artifact, release-asset, and dependency-snapshot upload
switches. The exact action source pins its default Syft tool, and this workflow
also sets that input explicitly to official
[Syft v1.51.1](https://github.com/anchore/syft/releases/tag/v1.51.1), published
2026-08-27. The reviewed Syft commit reported by that release binary is
`91a0032987d91b7411b52f6f5c185c5e7f775495`.

The action itself must download the pinned Syft installer and release binary
from Anchore's official GitHub release paths. Generation therefore has a
GitHub network dependency. Validation is local and has no network dependency.
The action receives no GitHub token or registry credentials; its dependency
snapshot, workflow-artifact, and release-asset uploads are all explicitly
`false`. An empty Docker configuration is supplied, and the `docker:` source
prefix forces the already-built local Docker images rather than a registry
source. The only later upload is the repository's separately gated, exact-byte
release-candidate stage.

The reviewed action's exact
[Syft invocation source](https://github.com/anchore/sbom-action/blob/3ad7283483fc7af8ff2b4ea19663c2d5ca935e26/src/github/SyftGithubAction.ts)
passes the `image` input directly to Syft, disables Syft's update check, and
supports both `spdx-json` and native `json` output. Syft documents the explicit
[`docker` source](https://github.com/anchore/syft/wiki/supported-sources) and
the two retained [output formats](https://github.com/anchore/syft/wiki/output-formats).

## CI lane

The workflow:

1. builds `crypto-lending-api:ci` and `crypto-lending-web:ci` with the exact
   canonical OCI source label and revision metadata and with BuildKit
   provenance attestations disabled (`--provenance=false`);
2. verifies the hardened runtime boundary;
3. creates a new physical `.local-validation/production-sbom` directory and an
   empty Docker credential directory;
4. captures the two distinct local Docker `.Id` values, saves each tagged image
   once, re-inspects the tag, and retains only the bounded raw index, manifest,
   and config JSON needed to prove the local descriptor chain;
5. scans `docker:sha256:<captured-id>` for each image, retaining both SPDX 2.3
   JSON and native Syft JSON from the same captured local input;
6. re-inspects the API and web tags after all four scans and requires them to
   still resolve to the captured IDs;
7. cross-validates the saved-image chain, native record, and SPDX inventory;
   and
8. only then creates the release-candidate manifest, which hashes and stages
   all six exact byte streams.

The generated files are:

- `.local-validation/production-sbom/api-image.spdx.json`
- `.local-validation/production-sbom/api-image.syft.json`
- `.local-validation/production-sbom/api-image.binding.json`
- `.local-validation/production-sbom/web-image.spdx.json`
- `.local-validation/production-sbom/web-image.syft.json`
- `.local-validation/production-sbom/web-image.binding.json`

Syft generates a fresh `creationInfo.created` timestamp and UUID-bearing
`documentNamespace` in each SPDX scan. The repository does not normalize or
rewrite them. The release manifest binds the exact generated bytes and their
SHA-256 digests, including both native records and both local archive-chain
records.

## Fail-closed validation

`scripts/validate-production-sboms.mjs` reads no network resource and starts no
subprocess. It derives exact required package versions from the checked-in
workspace manifests and lockfile, then requires:

- SPDX 2.3, the Syft 1.51.1 creator, Anchore image namespace, and bounded known
  document fields;
- the captured local ID in the SPDX document/root version and purl, one
  Syft container root, and a self-consistent root manifest SHA-256/purl;
- contained Nest runtime packages for the API and Next/React/React DOM for the
  web image at the exact locked versions; and
- unique package/file IDs, self-contained relationship endpoints, unique
  relationships, valid checksums, and safe image file paths.

For each native Syft record, validation additionally requires:

- `source.metadata.userInput` and `source.version` to equal the captured Docker
  ID, with the expected single `crypto-lending-{api|web}:ci` tag and
  `name@captured-id` repo digest;
- exact `amd64`/Linux identity and canonical OCI title, source URL, and source
  revision labels;
- SHA-256 verification of the retained base64 manifest and image-config bytes,
  descriptor/config/layer consistency, and the expected Syft 1.51.1 native
  schema 16.1.10;
- remote license lookup, Maven network use, and C++ package-manager git clone
  disabled in Syft's recorded configuration; and
- the same synthetic manifest digest, file count, package count, and sorted
  package name/version multiset as the paired SPDX document.

For each local archive-chain record, the capture and validator additionally
require:

- the tag to resolve to the expected captured ID both immediately before and
  immediately after `docker image save`;
- an exact SHA-256/size/media-type chain from that ID through either an OCI
  index and one unique Linux/amd64 runtime manifest, a single runtime manifest,
  or a classic Docker config root;
- rejection of duplicate descriptors, ambiguous platforms, attestation
  substitution, special or duplicate tar entries, unsafe paths, oversized
  archives/entries, and any descriptor/blob mismatch; and
- exact byte equality between the archive config and Syft's embedded config.
  The config's ordered `rootfs.diff_ids` must then equal Syft's ordered
  synthetic-manifest layer digests. OCI/Docker archive manifest layer digests
  identify compressed layer payloads, so they are deliberately compared to
  `rootfs.diff_ids` only by order/cardinality, never falsely asserted equal.

It rejects the explicitly forbidden development toolchain packages (including
`@solana/web3.js`), npm, pnpm, Yarn, Corepack, a fake or swapped image ID,
changed tag mapping, forged content digests, cross-format divergence,
missing/extra malformed identity fields, duplicate image IDs, reused document
identity, malformed JSON, symbolic links, hard links,
non-regular/empty/changed/oversized files, and aliased paths. The six input
paths are fixed by the CLI rather than caller-selectable.

Every checked-in package manifest and lockfile input and every generated SPDX,
native Syft, and archive-binding input is read twice through one stable file
descriptor. The second pass is compared byte-for-byte with the retained first
pass while identity, link count, size, and nanosecond timestamps remain fixed;
a same-size concurrent rewrite therefore fails the release gate.

Docker may expose a local OCI index digest, manifest digest, or classic config
digest as `.Id`, while Syft's Docker-daemon source records a synthesized
platform-manifest digest and the image-config digest. Those values are reported
separately and are not assumed equal. The trust root for this lane is the
captured local ID plus the independently parsed `docker image save` descriptor
chain and its exact config bytes. Syft's input/version/tag/repo-digest and OCI
label fields are metadata corroboration, not the binding root. This establishes
local source-image/config/rootfs association only. It does not establish
registry immutability, scanner truth or completeness, build provenance, a
signature, release approval, or deployment authorization.

For already generated local files:

```powershell
$ApiImageId = docker image inspect --format '{{.Id}}' crypto-lending-api:ci
$WebImageId = docker image inspect --format '{{.Id}}' crypto-lending-web:ci
$SourceRevision = git rev-parse HEAD
npm run production:sbom:capture -- api crypto-lending-api:ci `
  $ApiImageId .local-validation/production-sbom/api-image.binding.json
npm run production:sbom:capture -- web crypto-lending-web:ci `
  $WebImageId .local-validation/production-sbom/web-image.binding.json
npm run production:sbom:validate -- `
  $ApiImageId `
  $WebImageId `
  $SourceRevision
```

The focused offline suite is `npm run test:production:sbom`; the related lint
lane is `npm run lint:production:sbom`.

## Retired npm path

The earlier `npm sbom --package-lock-only --omit=dev` generator was removed. In
the exact current npm 11.6.4 lock state it omitted required Nest and React
runtime packages, so retaining it would have presented a known-incomplete path
as a production generator. No waiver was added; the image-derived lane replaces
it.

## Remaining release work

The SBOM action downloads tooling during CI, and the generated SPDX documents
are unsigned. The release still needs reviewed vulnerability scanning and
disposition, immutable OCI digest binding, signed provenance/signatures,
durable retention, registry publication controls, and deployment/rollback
evidence before public production use.
