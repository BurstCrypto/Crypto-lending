# KAN-246: Correlated job-envelope rollout preflight

KAN-246 supplies an offline, deterministic compatibility preflight and the
handoff plan for the correlated job envelope introduced by KAN-51. This branch
was created from local `main` at `eb455c80be4efdc18f347e3ee120fa70563df257`.
It does not deploy an image, connect to a database or queue, drain a worker,
invoke hosted CI, call AWS, or activate a paid service.

## Result and safety boundary

The preflight accepts a read-only JSON snapshot of every `pending`
`job_outbox` row. It emits a versioned report sorted by row ID, returns a
non-zero status when any row is incompatible, and never rewrites an envelope,
attribute, correlation identifier, or database row. Reports identify rows and
reason codes but omit payloads and attribute values.

The checked-in example is synthetic. No environment inventory attestation,
actual pending-row snapshot, worker drain, rollout, or rollback was executed.
Those actions require an explicitly named environment, approved revision,
authorized operators, and any applicable cost approval.

## Compatibility boundary

The old wire contract had no `correlation` object and allowed seven custom SQS
message attributes. The correlated contract reserves a fourth transport
attribute, `correlationId`, leaving six custom attributes. A correlation-less
legacy body can be projected to a deterministic `legacy:<sha256>` root only
when the remaining wire contract is safe.

The preflight fails a row for each applicable closed reason code:

| Reason code                          | Meaning                                                                                              |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| `ROW_INVALID`                        | The snapshot row itself is not the exact data-only contract.                                         |
| `ENVELOPE_SHAPE_UNSUPPORTED`         | Top-level keys are neither the exact legacy nor correlated shape.                                    |
| `ENVELOPE_INVALID`                   | Required ID, kind, version, timestamp, correlation, or payload structure is invalid.                 |
| `MESSAGE_ATTRIBUTES_INVALID`         | Attributes are not a plain, valid, string-only SQS record.                                           |
| `RESERVED_ATTRIBUTE_COLLISION`       | A custom name case-insensitively collides with `correlationId`, `jobId`, `jobKind`, or `jobVersion`. |
| `LEGACY_SEVEN_ATTRIBUTE_ENVELOPE`    | A legacy row consumes the former seven-custom-attribute capacity.                                    |
| `TOO_MANY_CUSTOM_ATTRIBUTES`         | Another shape has more than six custom attributes.                                                   |
| `JSON_DEPTH_EXCEEDED`                | Projected correlated JSON exceeds depth 64.                                                          |
| `JSON_NODE_LIMIT_EXCEEDED`           | Projected correlated JSON exceeds 100,000 nodes.                                                     |
| `MESSAGE_SIZE_HEADROOM_INSUFFICIENT` | Adding the correlated body/attribute metadata would exceed 1 MiB.                                    |
| `MESSAGE_SERIALIZATION_INVALID`      | The projected body contains another unsupported JSON form.                                           |

Exact-boundary tests cover depths 64/65, node counts 100,000/100,001, and
message sizes 1 MiB/1 MiB plus one byte. Separate cases cover the legacy
seven-attribute shape, case-insensitive reserved collisions, and superseded
top-level correlation fields. A repeat run over the same snapshot must produce
the same report bytes.

## Offline workflow

Run the synthetic fixture without a database, queue, container, or network:

```powershell
npm run outbox:preflight:envelope -- docs/outbox/kan-246-preflight-snapshot.example.json
```

The example intentionally contains incompatible rows, so the command writes
the full report and exits non-zero. A rollout snapshot is acceptable only when
`incompatibleRows` is zero. `legacyRows` may be non-zero only if the release
owner explicitly accepts deterministic correlation normalization under the
fail-closed legacy decision below.

After an environment-specific drain is separately authorized, an operator can
capture a statement-consistent, read-only snapshot with
[`scripts/sql/kan-246-pending-envelope-snapshot.sql`](../scripts/sql/kan-246-pending-envelope-snapshot.sql).
Use a read-only database identity, `psql --no-psqlrc --no-align
--tuples-only --quiet --set ON_ERROR_STOP=1`, and an output mechanism that
preserves UTF-8 JSON. Record the environment, exact database snapshot time,
row count, command version, and SHA-256 of both input and report. Do not put a
database URL, password, payload, attribute value, or raw snapshot in Jira or a
log record.

The checked-in query addresses `public.job_outbox` explicitly. This prevents a
temporary or earlier-`search_path` relation from substituting a different table
and producing false rollout evidence. If an approved environment does not use
the production `public` schema contract, stop and review an environment-specific
query rather than editing the relation name during the run.

The snapshot query includes every pending row, including a mistakenly leased
one. Before capture, a separate query must prove no pending row has
`locked_by IS NOT NULL` or an unexpired `locked_until`; otherwise the drain is
incomplete and the snapshot must not be accepted.

Superseded contracts requiring explicit attestation include correlation-less

top-level correlation fields, class/`toJSON` payloads, and consumers expecting
failure `error` fields instead of the closed `errorCode` result.

## Legacy enrichment decision

Decision state: **REJECT / fail closed until a separate approval is recorded.**

A normalized `legacy:*` correlation proves only deterministic linkage to an
opaque historic job ID. It does not prove an actor, account, intent, quote,
transaction, or ledger event. Runtime guards therefore prohibit binding an
actor or adding domain identifiers to a legacy root. Operators and handlers
must not infer those identifiers from payload data, look them up and attach
them, replace the root, or emit an enriched child envelope.

Changing this decision requires Security and the owning domain team to define
authoritative source records, ambiguity handling, authorization, audit
evidence, and a one-way migration contract. Until then, a legacy row is either
accepted with only its deterministic legacy root or held for an explicit
disposition; it is never silently enriched.

## Coordinated drain and rollout order

Trey is the KAN-246 rollout coordinator. Platform/Release Engineering executes
the environment run; API/Ledger Backend and every independently deployed
producer/consumer owner must sign the inventory for the exact revision.

1. Record the target environment, reviewed Git SHA/image digests, queue and
   database identities, change window, rollback owner, and cost authorization.
2. Freeze releases and configuration changes. Complete the external inventory;
   an unknown producer or consumer is a hard stop.
3. Prevent every old producer from creating new outbox or direct SQS work.
   Confirm the correlated producer revision is available but do not start it.
4. Gracefully stop the old outbox dispatcher. Wait for in-flight sends and all
   database leases to clear. Do not force-expire or rewrite a lease.
5. Capture the read-only pending-row snapshot and its SHA-256. Confirm snapshot
   row count equals the drained database pending count.
6. Run the offline preflight twice with the exact reviewed code. Require equal
   report hashes, zero incompatible rows, and an approved decision for any
   compatible legacy rows.
7. If any row is incompatible, keep the rollout stopped. Choose an explicit
   disposition: postpone the release, allow the reviewed old worker to drain
   it while producers remain frozen, or open a separately reviewed data-change
   plan. Never rewrite, drop, republish, or chain it as part of this preflight.
8. Once clean, update consumers before producers. Start only consumers proven
   to accept both exact legacy and correlated bodies, then the correlated
   outbox dispatcher, then correlated API/direct producers.
9. Verify pending count, publication/failure counts, queue age, retries, and
   DLQ state using approved low-cardinality evidence. Bind the results to the
   exact snapshot, report, and deployed revisions.
10. Close the freeze only after every owner confirms normal processing and the
    rollback window has ended.

No step above was executed by this local ticket branch.

## Rollback

- Before a new message is published, stop and leave the snapshot rows intact;
  resume only the exact old producer/worker set covered by the inventory.
- After correlated publication begins, stop producers and the outbox dispatcher
  first. Preserve pending rows, queue messages, receive counts, and DLQ data.
  Do not delete, redrive, or reconstruct a message to make an old consumer fit.
- Restart an older consumer only if its attestation proves it accepts every
  already-published body and attribute shape. Otherwise use a reviewed
  roll-forward consumer that accepts both contracts.
- Reconcile database row IDs to transport receipts and handler audit records
  before resuming. Idempotency controls, not manual resubmission, govern any
  uncertain publication.
- Record the stop point, owner, reason, retained evidence, and final disposition.

## Unresolved release gates

- Complete the independently deployed producer/consumer inventory and name the
  production business-job consumer owner.
- Choose the exact environment and bind approvals to its database, queue,
  revisions, access boundary, change window, and cost ceiling.
- Approve or reject processing of compatible `legacy:*` rows for that rollout.
- Define a separately reviewed disposition for each incompatible pending row.
- Decide whether legacy actor/domain enrichment will ever be permitted; the
  current decision remains reject.
- Capture actual drain, snapshot/report hashes, rollback readiness, and post-run
  reconciliation evidence.

Until every gate is closed, KAN-246 provides local readiness evidence only and
must not be represented as an executed rollout.
